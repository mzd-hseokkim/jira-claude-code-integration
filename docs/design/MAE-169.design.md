# Design: MAE-169 - [1.1.10] discover 합성 결과에 Trace Marker 자동 부여

## Overview

본 설계는 `jira-task-discover` 스킬의 Step 2/3/4 본문과 Inline Fallback Template에 출처 추적 marker(trace marker) 부여 규칙을 surgical하게 추가하기 위한 문서 변경 설계다. 코드 동작은 LLM 추론 가이드(SKILL.md) 변경으로 한정되며 신규 파일 생성·외부 호출·기존 산출물 retrofit은 포함하지 않는다.

- **Plan 참조**: `docs/plan/MAE-169.plan.md`
- **변경 대상 스킬**: `skills/jira-task-discover/SKILL.md`
- **변경 대상 메타**: `.claude-plugin/plugin.json` (version)
- **참고 design**: `docs/design/MAE-117.design.md` (Inline Fallback Template과 외부 템플릿 매핑)

### Decision: Marker 형식의 단일 출처 (Single Source of Truth)

| 후보 | 위치 | 채택 여부 | 사유 |
|------|------|----------|------|
| 외부 템플릿 (`templates/requirements.template.md`)에 형식 정의 | 외부 파일 | X | MAE-171의 책임 영역. 본 이슈는 SKILL.md만 surgical 편집 |
| SKILL.md Step 4 본문에 표 형태로 4가지 형식 정의 | 워크플로 본문 | **O** | 워크플로와 형식이 한 곳에서 보임. LLM이 추론 시 동일 파일 내에서 참조 |

**결론**: 본 이슈가 marker 형식 표준의 단일 출처(SSOT)다. SKILL.md Step 4 본문에 4가지 형식을 표 형태로 명시하고, MAE-171은 이 형식을 그대로 외부 템플릿에 복제한다.

### Decision: Marker 부여 대상의 경계

| 섹션 | 출처 성격 | marker 대상 여부 |
|------|----------|----------------|
| Stakeholders | Step 3 답변 1번 직접 매핑 | X (출처 자명) |
| Goals & Success Criteria | Step 3 답변 2번 직접 매핑 | X (출처 자명) |
| Constraints | Step 3 답변 3번 직접 매핑 | X (출처 자명) |
| Non-functional Requirements | Step 3 답변 4번 직접 매핑 | X (출처 자명) |
| Codebase Context | Step 2 결과 직접 매핑 | X (출처가 메타로 이미 보존됨) |
| **Functional Requirements** | 답변+코드+LLM 합성 | **O** |
| **Edge Cases** | 답변+코드+LLM 합성 (`--lite` 시 섹션 통째 생략) | **O** |
| **Out of Scope** | 답변+코드+LLM 합성 (`--lite` 시 섹션 통째 생략) | **O** |
| **Open Questions** | 답변 부족/TBD 항목 | **O** |

**결론**: 비대상 5종은 답변·메타가 이미 곧 출처이므로 marker 불요. 대상 4종(FR/Edge Cases/Out of Scope/Open Questions)에만 항목 단위 marker를 부여한다.

### Decision: 다중 출처 표기 규칙 (Plan Edge Cases 후속 확정)

Plan의 Edge Cases에서 design 단계 확정 사항으로 미뤘던 항목들의 결정.

| 케이스 | 표기 규칙 |
|--------|----------|
| 단일 답변에서 유래 | `*(source: Q2)*` |
| 단일 코드 위치에서 유래 | `*(code: src/notify.ts:45-60)*` |
| 답변 + 코드 (각 1) | `*(source: Q2, code: src/notify.ts:45-60)*` |
| **여러 답변에서 유래** | `*(source: Q1, Q3)*` (콤마 구분, 최대 3개까지. 4개 이상이면 단일 표기 원칙으로 가장 강한 1개만) |
| **여러 코드 위치에서 유래** | `*(code: src/a.ts:10-20, src/b.ts:5-15)*` (콤마 구분, 최대 2개까지. 3개 이상이면 가장 대표적 1개만) |
| 답변·코드 어디에도 근거 없음 | `*(synthesized)*` |

원칙: **가독성보다 추적성 우선**. 단, 항목 끝 marker가 본문보다 길어지면 가독성이 깨지므로 multi 항목 상한을 위처럼 둔다.

### Decision: `--from` 모드의 marker 처리 (Plan Edge Cases 후속 확정)

Plan에서 design 단계 결정으로 미룬 항목.

| 케이스 | 표기 |
|--------|------|
| `--from` import 본문에서 그대로 가져온 항목 | `*(source: from)*` |
| `--from` import 본문에 보강이 추가된 항목 | `*(source: from, Q<N>)*` 또는 `*(source: from, code: ...)*` |
| `--from` 본문 외 합성 추가 항목 | default 모드 규칙 그대로 (`Q<N>` / `code:` / `synthesized`) |

**채택**: `*(source: from)*` 변형을 1개 추가한다. SKILL.md Step 4 본문 표에 case 하나로 박는다.

### Decision: `synthesized` 마커 사용 가이드

본 이슈의 핵심 위험(`*(synthesized)*` 남용)을 막기 위해 SKILL.md에 다음 규칙을 명시한다.

- **사용 가능 조건**: Q<N> 답변 어디에도 직접 근거가 없고, Step 2 코드 발췌 어디에도 직접 근거가 없는 LLM 자체 합성 항목에만 사용
- **권장 우선순위**: `Q<N>` 추적 > `code:` 추적 > 둘 다 > `synthesized`
- **Open Questions 섹션 예외**: Open Questions는 본질이 "결정 보류"이므로 `*(source: Q<N>)*`(어느 답변이 부족했는지)가 자연스럽다. `*(synthesized)*` 사용은 지양
- **Edge Cases 기본 marker**: Edge Cases는 거의 LLM 합성이라 `*(synthesized)*` 또는 `*(code: ...)*`가 일반적. 사용자 답변에서 직접 도출된 경우(예: "동시 호출 시 어떻게?"라는 답변)에 한해 `*(source: Q<N>)*`

```mermaid
sequenceDiagram
    participant User
    participant Discover as jira-task-discover
    participant FS as File System
    participant Doc as docs/requirements/&lt;slug&gt;.requirements.md

    Discover->>User: AskUserQuestion (4건 / --lite 시 3건)
    User-->>Discover: 답변
    Discover->>Discover: 답변에 Q1, Q2, Q3, Q4 인덱스 부여<br/>(--lite 시 Q1~Q3)

    Note over Discover: Step 4: Generate Requirements Document
    Discover->>Discover: 합성 4종(FR/Edge/OOS/OQ) 생성
    loop 각 합성 항목마다
        Discover->>Discover: 출처 판정<br/>(Q<N> 답변 / Step 2 메타 / LLM 합성)
        Discover->>Discover: marker 부여<br/>(source / code / 둘 다 / synthesized / from)
    end
    Discover->>Doc: Write (각 항목 끝에 marker 부착)
    Doc-->>User: marker 표기된 요구사항 문서
```

핵심 변경점:
- Step 2: 결과 캡처 시 `(file_path, line_range)` 메타 보존이 명시됨 (이전: 단순 발췌)
- Step 3: 답변에 `Q<N>` 인덱스가 부여됨 (이전: 인덱스 없음)
- Step 4: 합성 4종 항목 끝마다 출처 판정 후 marker 부착 (이전: marker 없음)

### Step 2 본문 추가 사항 (개념 수준)

- 결과를 `(file_path, line_range)` 형태로 보존한다는 한 줄 규칙
- `line_range` 표기 예시: `src/notify.ts:45-60` (단일 line인 경우는 `:45`만 허용)
- `Glob` 결과는 파일 단위라 line_range는 후속 `Grep` 매칭 줄 또는 발췌 범위로 산출
- 이 메타가 Step 4 marker의 `code:` 부분에 그대로 인용된다는 한 줄 노트

### Step 3 본문 추가 사항 (개념 수준)

- 각 질문에 `Q1`~`Q4` 인덱스를 부여한다는 한 줄 규칙
- `--lite` 모드는 `Q1`~`Q3` (4번 NFR 제외)
- `--from` 모드에서 누락 항목만 묻더라도 원래 인덱스 유지 (예: NFR만 물으면 그 답변이 `Q4`)
- 이 인덱스가 Step 4 marker의 `source: Q<N>` 부분에 그대로 인용된다는 한 줄 노트

### Step 4 본문 추가 사항 (개념 수준)

추가 4묶음:

1. **Marker 부여 대상 명시**: FR/Edge Cases/Out of Scope/Open Questions 4종에 항목 단위로 marker 부여 (Stakeholders/Goals/Constraints/NFR/Codebase Context는 비대상)
2. **Marker 형식 표 (5 case)**: 본 design 문서의 "Decision: 다중 출처 표기 규칙" 표를 SKILL.md에 그대로 박음
3. **`synthesized` 가이드**: 본 design 문서의 "Decision: `synthesized` 마커 사용 가이드" 4 bullet을 그대로 박음
4. **`--from` 변형**: `*(source: from)*` / `*(source: from, Q<N>)*` 등 변형을 한 줄 노트로 박음

### Inline Fallback Template 갱신 (개념 수준)

L180-247 본문에서 다음 placeholder들 끝에 marker 자리를 추가:

- `## Functional Requirements` 섹션의 `1. <Req-1>`, `2. <Req-2>` → `1. <Req-1> *(source: Q<N>, code: <path>:<line>)*` 등 marker 자리 명시
- `## Edge Cases` 섹션의 `- <Edge case 1>` → `- <Edge case 1> *(synthesized)*` 또는 `*(code: <path>:<line>)*` 자리 명시
- `## Out of Scope` 섹션의 `- <Item 1>` → `- <Item 1> *(source: Q<N>)*` 또는 marker 자리 명시
- `## Open Questions` 섹션의 `- <Q1>` → `- <Q1> *(source: Q<N>)*` 자리 명시

placeholder는 LLM이 모방하기 위한 예시이므로 **모든 marker 형식 4가지가 적어도 한 번씩** 등장하도록 분배한다.

### plugin.json 버전 증가

- 현재: `0.15.1`
- 변경 후: `0.15.2`
- 사유: SKILL.md 동작 가이드 변경 (LLM 추론 결과 형식이 바뀌므로 patch+1이 적절. minor는 의미상 과함)

### Implementation Sequence

1. SKILL.md Step 2 → Step 3 → Step 4 순서로 본문 추가 (의존 순서: Step 2/3가 Step 4 marker의 입력)
2. Step 4 본문에 marker 형식 표·`synthesized` 가이드·`--from` 변형 추가

5. (test 단계) discover 스킬을 sample topic으로 dry-run 호출하여 marker 일관 부여 검증

## Interfaces / Types

본 이슈는 코드 변경이 없으므로 타입/인터페이스 정의는 마크다운 placeholder 형식만 명시한다.

| 이름 | 역할 |
|------|------|
| `(file_path, line_range)` 튜플 | Step 2 결과의 메타 보존 단위. line_range 표기는 `<path>:<start>-<end>` 또는 `<path>:<line>` |
| `Q<N>` 인덱스 | Step 3 답변별 인덱스. N은 1-4 (default) 또는 1-3 (`--lite`) |
| `*(source: Q<N>)*` | 답변 1개에서 유래한 항목의 marker |
| `*(source: Q<N>, Q<M>)*` | 답변 다수에서 유래한 항목의 marker (최대 3개) |
| `*(code: <path>:<line-range>)*` | 코드 1곳에서 유래한 항목의 marker |
| `*(code: <path1>:<r1>, <path2>:<r2>)*` | 코드 다수에서 유래한 항목의 marker (최대 2개) |
| `*(source: Q<N>, code: <path>:<line>)*` | 답변+코드 결합 marker |
| `*(synthesized)*` | LLM 창의적 합성 (답변·코드 어느 쪽에도 근거 없음) |
| `*(source: from)*` | `--from` 모드에서 import 본문 그대로 |
| `*(source: from, Q<N>)*` / `*(source: from, code: ...)*` | `--from` import + 보강 |

## Error Handling

| 시나리오 | 처리 전략 |
|---------|----------|
| Step 2 결과가 0건 | 모든 합성 항목이 `*(source: Q<N>)*` 또는 `*(synthesized)*`로 한정. 자연스러운 케이스이므로 별도 처리 없음 |
| Step 3 모든 답변이 `TBD` | `*(source: Q<N>)*`로 표기 가능하되 본문이 `TBD`. 합성 항목은 `*(synthesized)*` 또는 `*(code: ...)*`만 남음. 사용자에게 "답변 부족 — 산출물 신뢰도 낮음" 경고는 필요 시 Confirm Gate(MAE-168) 영역 |
| LLM이 marker 형식 일관 부여 실패 (예: 괄호/이탤릭 누락) | SKILL.md Step 4 본문에 4가지 형식 코드 블록 + Inline Fallback placeholder에 marker 자리 명시 (LLM이 모방하기 쉽게). 자동 검증/lint는 본 이슈 Out of Scope (MAE-171 또는 후속 lint 이슈) |
| `--from` 본문이 marker 없는 구형 산출물 | import 본문 항목에 `*(source: from)*` 일괄 부여. retrofit은 안 함 (Out of Scope). 보강 시 `*(source: from, Q<N>)*`로 갱신 |
| 한 항목이 4개 이상 답변에서 유래 | 단일 표기 원칙으로 가장 강한 1개만 표기 (SKILL.md에 명시) |
| 한 항목이 3개 이상 코드 위치에서 유래 | 가장 대표적 1개만 표기 (SKILL.md에 명시) |
| Inline Fallback Template과 외부 `templates/requirements.template.md` 형식 충돌 | 본 이슈가 SSOT — 외부 파일은 MAE-171이 본 이슈의 형식으로 재정의 |
| 기존 산출물(`docs/requirements/*` marker 없음)과 신규 산출물 일관성 부족 | Out of Scope. 신규 호출부터 marker 적용. 기존 문서 호환 (정보 추가만) |
| `.claude-plugin/plugin.json` version 증가 누락 | impl 단계 체크리스트 + test 단계 검증 (test에서 plugin.json 확인) |
| `--lite` 모드에서 marker 규칙 충돌 | `--lite`는 Edge Cases / Out of Scope 섹션이 통째 생략되므로 marker 적용 대상이 자연 축소 (FR/Open Questions 2개). SKILL.md `--lite` 본문에 한 줄 명시 |

## Security Checklist

본 이슈는 외부 API/네트워크 호출이 없고, 입력은 LLM 컨텍스트 내 텍스트로 한정되므로 보안 위협 표면이 좁다. 그래도 marker가 코드 경로를 산출 문서에 노출하므로 다음을 점검한다.

- [ ] **민감 경로 노출**: marker의 `<path>:<line>`이 비공개 디렉터리(`.env`, `.claude/settings.local.json` 등)를 가리키지 않는지 확인. 산출 문서가 Jira 첨부로 갈 수 있음을 고려해 SKILL.md Step 2 본문에 "민감 파일 발췌 금지" 가이드를 한 줄 추가 검토 (test 단계 sanity check 항목)
- [ ] **자격증명 누출**: Step 2의 30줄 발췌가 토큰/키를 포함하지 않도록 기존 발췌 가이드 유지 (본 이슈로 새 위협 추가 없음)
- [ ] **사용자 답변 sanitize**: Q<N> 인덱스 부여만으로 답변 본문 sanitize는 변경 없음. 답변에 악성 markdown(`<script>` 등)이 들어와도 산출물은 로컬 .md 파일이라 실행 위험 없음
- [ ] **`--from` 외부 파일 신뢰 경계**: 기존 SKILL.md L256(파일 부재) / L264(`--lite`+`--from` 병용) 처리 그대로. `*(source: from)*` 추가는 신뢰 경계를 넓히지 않음
- [ ] **plugin.json version**: 잘못된 형식(non-semver) 입력 방지. 단순 patch+1이라 위험 낮음

## Test Plan

본 이슈는 코드가 아닌 SKILL.md(LLM 가이드) 변경이므로 자동 unit test 작성은 어렵다. 대신 `/jira-task test` 단계에서 다음을 명세 단위로 수행한다.

### Test Type Scope

- **Unit test**: 해당 없음 (코드 산출물 없음)
- **Document inspection**: SKILL.md/plugin.json/Inline Fallback Template diff에 대한 grep/시각 검증
- **Dry-run sanity check**: discover 스킬을 sample topic으로 가상 호출하여 marker 일관성 확인

### Test Case Specifications

#### TC-1: SKILL.md Step 2에 코드 메타 보존 형식이 명시됨 (AC-1)
- 검증 방법: grep으로 SKILL.md L83-93 영역에 `(file_path, line_range)` 또는 `<path>:<line-range>` 키워드 존재 여부 확인
- 기대 결과: 매칭 1건 이상
- 경계 조건: 표기는 `(file_path, line_range)` 또는 동등한 한국어 설명. 형식 자체는 정확히 매칭되지 않아도 의미가 동등하면 OK

#### TC-2: SKILL.md Step 3에 Q1~Q4 인덱스 규칙이 명시됨 (AC-2)
- 검증 방법: grep으로 SKILL.md Step 3 영역에 `Q1`, `Q2`, `Q3`, `Q4` 토큰 모두 존재 여부 확인. `--lite` 모드 본문에 `Q1~Q3` 또는 동등 표기 확인
- 기대 결과: 4건 모두 매칭 + `--lite` 케이스 명시
- 경계 조건: `Q<N>` 형식의 placeholder도 인정 가능

#### TC-3: SKILL.md Step 4에 marker 형식 4종 모두 명시됨 (AC-3)
- 검증 방법: SKILL.md Step 4 영역에서 다음 4 패턴 grep
  1. `*(source: Q<N>)*` 또는 `*(source: Q1)*` 등 구체 예시
  2. `*(code: <path>:<line-range>)*` 또는 구체 예시
  3. `*(source: Q<N>, code: <path>:<line>)*` 또는 구체 예시
  4. `*(synthesized)*`
- 기대 결과: 4 패턴 모두 매칭
- 경계 조건: 표 형태 또는 코드 블록 어느 쪽이든 인정. 다만 사용자가 한 곳에서 4 패턴을 모두 볼 수 있어야 함

#### TC-4: Inline Fallback Template placeholder에 marker 자리 추가됨 (AC-4)
- 검증 방법: SKILL.md L180-247 영역에서 다음 4 섹션의 placeholder 끝에 marker 자리(`*(...)*` 패턴) 존재 확인
  - `## Functional Requirements` placeholder
  - `## Edge Cases` placeholder
  - `## Out of Scope` placeholder
  - `## Open Questions` placeholder
- 기대 결과: 4 섹션 모두 marker 자리 포함
- 경계 조건: 모든 marker 형식 4가지(`source` only / `code` only / 둘 다 / `synthesized`)가 placeholder 본문 어딘가에 적어도 한 번씩 등장 (LLM 모방 학습용)

#### TC-5: SKILL.md에 `synthesized` 가이드가 명시됨 (AC-5)
- 검증 방법: grep으로 SKILL.md Step 4 영역에 `synthesized` 마커의 사용 조건(예: "답변·코드 어느 곳에도 근거가 없을 때만") 문구 존재 확인
- 기대 결과: 1건 이상 매칭
- 경계 조건: 정확한 문구 일치는 불요. "근거 없음", "LLM 합성" 등 의미가 통하면 OK

#### TC-6: `--lite` 모드 정합성 명시 (AC-6)
- 검증 방법: SKILL.md에서 `--lite` 모드 본문에 marker 규칙이 일관 적용된다는 노트 존재 확인. 또는 marker 부여 대상이 FR/Open Questions 2개로 자연 축소된다는 노트
- 기대 결과: 1건 이상 매칭
- 경계 조건: `--lite` 본문 기존 라인(L108, L136 등)에 추가되거나 별도 한 줄 노트로 추가

#### TC-7: Surgical change 검증 (AC-7)
- 검증 방법: `git diff main...feature/MAE-169 -- skills/`로 변경 파일 목록 확인. SKILL.md(jira-task-discover) 외 파일이 변경되지 않았는지 확인
- 기대 결과: `skills/jira-task-discover/SKILL.md`만 변경됨
- 경계 조건: 다른 jira-task-* 스킬 SKILL.md, `commands/jira-task.md`, `templates/*` 등이 변경되지 않아야 함

#### TC-8: plugin.json version 증가 (AC-8)
- 검증 방법: `.claude-plugin/plugin.json`의 `version` 값을 main 브랜치와 비교. 본 PR에서 patch 또는 minor +1 확인
- 기대 결과: `0.15.1` → `0.15.2` (또는 그 이상)
- 경계 조건: semver 형식 유지

#### TC-9: Dry-run sanity check
- 검증 방법: 가상 topic(예: "사용자 알림 시스템")으로 discover 스킬 워크플로를 추적하여 합성 항목에 marker가 일관 부여되는지 확인. 실제 LLM 호출 없이 SKILL.md 본문을 따라 mental walk-through 또는 minimum-viable 호출
- 기대 결과: FR 항목마다, Edge Cases 항목마다, Out of Scope 항목마다, Open Questions 항목마다 marker가 1개씩 붙음. 형식은 4 표준 중 하나
- 경계 조건: marker 형식 위반(괄호 누락/이탤릭 누락) 시 SKILL.md 본문 수정 필요. 본 test 단계에서 회귀
- 비고: LLM 추론 결과는 비결정적이므로 1회 sanity check로 충분 (CI 자동 검증은 후속 이슈)

#### TC-10: Jira 첨부 marker 노출 검토 (Security Checklist 후속)
- 검증 방법: dry-run 결과의 `code:` 경로가 비공개 디렉터리(`.env`, `.claude/settings.local.json`, `node_modules/` 등)를 가리키지 않는지 확인
- 기대 결과: 모든 `code:` 경로가 공개 코드 영역(`src/`, `skills/`, `docs/` 등) 내
- 경계 조건: 위반 시 SKILL.md Step 2에 "민감 파일 제외" 한 줄 추가 검토

### Test Execution Sequence

1. impl 단계 완료 후 git diff로 변경 영역 1차 검토
2. TC-1 ~ TC-8까지 grep/diff 기반 자동 검증
3. TC-9 dry-run sanity check (가상 topic 1건)
4. TC-10 보안 체크 (TC-9 결과 부산물 활용)
5. 결과를 `docs/test/MAE-169.test-report.md`에 기록 후 Jira 코멘트 게시
