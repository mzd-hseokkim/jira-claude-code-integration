## Architecture

본 작업은 **신규 모듈 0개, 기존 SKILL.md 1개 수정**이다. 코드는 SKILL.md의 Step 4.7 블록(Bash + 내부 Python heredoc) 안에 인라인으로 작성된다.

- **신규 vs 수정 컴포넌트**:
  - 수정: `skills/jira-task-review/SKILL.md` (Step 4.7 신설, Step 4 / Step 5 / Step 6 본문 변경 없음)
  - 신규: 없음 (`scripts/review_log/redact.py`는 Story 1에서 이미 존재)
- **모듈 의존 방향**:
  - SKILL.md (Bash) → `python3 scripts/review_log/redact.py 경로의 sibling import` (one-shot heredoc)
  - heredoc 내부에서 `from review_log.redact import redact` (sys.path 조정으로 `scripts/`를 PYTHONPATH에 추가)
  - 외부 시스템 의존 없음 (Jira / 네트워크 호출 없음)
- **외부 시스템 경계**: in-process. Step 4.7은 로컬 파일 시스템(disk I/O)만 다룬다. Jira REST/MCP 호출은 Step 4.5와 Step 5가 담당하며 Step 4.7과 분리.

호출 흐름:

```
Step 4: subagent 결과 → docs/review/<TASK-ID>.review.md (기존)
        ↓
[NEW] Step 4.7: review.md 산출 직후 main 세션이 Bash 블록 실행
        ├── reviewerVersion = shasum -a 256 SKILL.md | head 12
        ├── REPO_ROOT/scripts를 PYTHONPATH에 추가
        ├── python3 -c heredoc:
        │     1) subagent 반환값(JSON 형태로 stdin 전달) 파싱
        │     2) outcome enum 매핑 (Approve→pass / Request Changes→fail / Needs Discussion→warn)
        │     3) findings[*].message에 redact() 적용
        │     4) severityCounts 5종 집계
        │     5) per-task JSON read-or-init → entries[] push → 원자적 rename으로 저장
        │     6) _index.jsonl에 한 줄 append
        │     7) 종료 코드 0
        └── 비zero 종료 시 stdout `⚠️ review-log append failed: <reason>`
        ↓
Step 4.5: 첨부 업로드 (기존)
Step 5:   Jira 코멘트 (기존)
Step 6:   Completion Summary (기존)
```

## Key Decisions

| # | 결정 | 대안 | 이유 |
|---|---|---|---|
| K1 | Python heredoc 1회 호출로 통합 (Bash sed redact 사용 안 함) | (a) Bash sed 인라인 regex, (b) Python 호출 2회 (per-task JSON, _index.jsonl 분리) | (a)는 Story 1 패턴 6종 중 일부(JWT, generic_secret 캡처그룹)가 sed로 정확히 표현 안 됨 + 패턴 동기화 부채. (b)는 AC-7(200ms) 마진을 깎는다. Python 1회 spawn(~30~80ms) + 단일 transaction이 단순 |
| K2 | per-task JSON 저장 시 **temp file + rename** (원자적 swap) | 직접 truncate-write | review 도중 실패 시 기존 entries[]가 손실되는 것을 방지. AC-2의 "truncate 금지" 보장 |
| K3 | `_index.jsonl`은 append-only `open(path, "a")` | rewrite | POSIX `O_APPEND` 원자성 활용. 한 줄 ≪ 4096B로 PIPE_BUF 보장 |
| K4 | reviewerVersion = `shasum -a 256 <skill_dir>/SKILL.md \| cut -c1-12` | git 해시, 파일 내용 sha + agents 합산 | plan Scope Decision #2 그대로. SKILL.md 절대경로는 본 스킬 실행 중인 base directory(이 SKILL.md 자신)를 가리키도록 `${BASH_SOURCE[0]}` 또는 스킬 base 경로를 사용 (Risks #3 대응) |
| K5 | subagent 결과 → Python으로 전달 방식: **JSON 파일 임시 저장 후 인자로 경로 전달** | stdin pipe, Bash 변수 export | subagent 반환값에 multi-line + 따옴표 포함 가능 → Bash 변수 escape 부담 큼. 임시 파일이 가장 견고 (`mktemp` + trap rm) |
| K6 | severityCounts 5종 schema(`critical/high/medium/low/info`) 사용 — plan 본문(3종)은 무시 | plan 본문의 3종({critical, warning, info}) 사용 | Story 1(MAE-179, 완료) schema가 단일 source of truth. plan 작성 시 schema와의 정합성 누락 — Open Items에 기록 |
| K7 | subagent의 Critical/Warning/Info 분류 → schema severity 매핑: Critical→critical, Warning→high, Info→info (medium/low는 미사용, 0으로 채움) | Warning을 medium으로 매핑 | Critical 외 finding은 보수적으로 high로 잡아 분석 시점에 가시성 우선. medium/low는 schema 호환을 위해 키만 0으로 유지 |
| K8 | _index.jsonl 라인은 schema README의 4필드 그대로 (`taskId`, `timestamp`, `outcome`, `severityCounts`) | 추가 메타(reviewerVersion 등) 포함 | schema 명세 준수. 분석에 reviewerVersion 필요하면 per-task JSON join 가능 |

## Data Model

스키마는 Story 1 산출물(`docs/review-log/README.md`)을 그대로 따른다. 본 design은 schema 변경 없음 — `N/A — no schema changes (Story 1 정의 그대로)`.

본 design에서 정의하는 **subagent 반환값 → schema entry 매핑**(타입 시그니처 수준만):

```
SubagentResult = {
  result: "Approve" | "Request Changes" | "Needs Discussion",
  findings: [{ severity: "Critical"|"Warning"|"Info", file: str, line: int, category: str, message: str }, ...],
  ...
}

→ Entry (schema-compliant) = {
  taskId: <TASK-ID>,
  timestamp: now_utc_iso8601_z(),
  reviewerVersion: <12-hex>,
  outcome: map_outcome(result),     # Approve→pass, Request Changes→fail, Needs Discussion→warn
  findings: [
    {
      id: f"F-{i:03d}",              # 1-based, 본 entry 내부 단조
      severity: map_severity(s),     # Critical→critical, Warning→high, Info→info
      file, line, category,
      message: redact(message),
    }
  ],
  severityCounts: {critical, high, medium, low, info},   # 5키 모두, 미사용은 0
  falsePositive: null,
  userOverride: null,
}
```

per-task JSON 컨테이너 형태 (재리뷰 누적 위해 `entries[]`로 wrap — schema README의 단일 entry 예시와 다름):

```
PerTaskFile = {
  schemaVersion: 1,
  taskId: <TASK-ID>,
  entries: [Entry, Entry, ...]   # append-only, 시간순
}
```

> schema README 예시는 단일 entry 형태이지만, plan AC-2가 "재리뷰 시 `entries[]`에 push"로 명시되어 있어 컨테이너로 wrap. **schema README와의 표면 차이**가 발생하므로 Open Items에 기록(Story 3 분석 스크립트가 컨테이너 형태를 인지해야 함).

## Error Handling

| # | 시나리오 | 유형 | 처리 |
|---|---|---|---|
| E1 | `docs/review-log/` 디렉터리 없음 | b (예측 가능 환경 상태) | `mkdir -p docs/review-log` 선실행 |
| E2 | 디스크 권한 없음 / read-only FS | a (외부 자원 실패) | try/catch → stdout `⚠️ review-log append failed: permission denied` → Step 5 진행 (AC-4) |
| E3 | per-task JSON 파일이 손상된 JSON | a (외부 데이터 결함) | Python에서 JSONDecodeError catch → 새 컨테이너로 재초기화 + stdout `⚠️ review-log append: existing per-task JSON corrupt, reinitialized` 후 진행. 기존 파일은 `<TASK-ID>.json.corrupt-<ts>`로 백업 |
| E4 | subagent 반환값이 비어있거나 schema 매핑 실패 (예: result 필드 누락) | a (상위 단계 결함) | best-effort: 가능한 필드만 채우고 누락 필드는 default(`outcome="warn"`, `findings=[]`, `severityCounts` zero) → stdout 경고. impl 진입 차단 안 함 |
| E5 | Python3 미존재 / sys.path 조정 실패 / `review_log` 모듈 import 실패 | a (환경 결함) | try/catch → stdout `⚠️ review-log append failed: redact module unavailable` → append 자체를 스킵. AC-6 미달 가능성 표시. 워크플로 비차단 |
| E6 | `_index.jsonl` 동시 append 시 줄 섞임 | c (이론상 가능, 실 발생률 낮음) | POSIX `O_APPEND`(< PIPE_BUF) 원자성 의존. Windows에서는 plan Risks대로 PR 단계 1회 수동 검증. 별도 락 미도입 (plan Scope Decision #4 = 재시도 없음과 일관) |
| E7 | reviewerVersion 산출(`shasum`) 실패 | a | reviewerVersion = `"unknown"` 으로 채우고 경고 출력. 워크플로 비차단 |

유형 범례 — a: 외부/상위 결함(throw 또는 grace-fallback), b: 예측 가능한 환경 상태(선처리), c: 이론상 가능하지만 실 발생률 낮음(가정 + 모니터링).

## Test Plan

### Unit (Python heredoc 단위 검증, 선택 — plan Task 6 nice)

heredoc 로직을 `scripts/review_log/append.py`로 추출하면 단위 테스트 가능. 본 design은 SKILL.md 인라인을 1차 안으로 두되, 추출 가능성을 Open Items로 둠.

추출 시 검증 케이스:
- U1: outcome enum 매핑 3종 (Approve/Request Changes/Needs Discussion → pass/fail/warn)
- U2: severity 매핑 3종 + medium/low 0 채움
- U3: redact 적용된 message가 entry에 저장됨
- U4: 기존 per-task JSON 컨테이너에 entries.append 동작 (truncate 안 됨)
- U5: 손상된 JSON 발견 시 백업 + 재초기화

### E2E (수동, AC 매핑)

| AC | 검증 절차 | 합격 기준 |
|---|---|---|
| AC-1 | 정상 review 1회 실행 → `ls docs/review-log/` | `<TASK-ID>.json` 존재(entries 길이 1) + `_index.jsonl` 1줄 |
| AC-2 | 같은 task로 review 2회 → 파일 내용 확인 | per-task `entries` 길이 2, `_index.jsonl` `wc -l` = 2 |
| AC-3 | subagent에 강제 Request Changes 시나리오 (디자인 미준수 코드) → review 실행 | `.jira-context.json`의 `completedSteps`에 `"review"` 없음 + `_index.jsonl` 1줄 추가됨 |
| AC-4 | `chmod -w docs/review-log/<TASK-ID>.json` 후 재 review | stdout `⚠️ review-log append failed: ...` 1줄 + Jira 코멘트 정상 게시 + 종료 코드 0 |
| AC-5 | 저장된 entry를 `python -m json.tool`로 파싱 후 필드 grep | `taskId/timestamp/reviewerVersion/outcome/findings/severityCounts/falsePositive/userOverride` 모두 존재 + `reviewerVersion`이 12자 hex + `severityCounts`가 5키 dict |
| AC-6 | finding message에 `sk-test-12345`, `Bearer abc.def.ghi`, `AKIAIOSFODNN7EXAMPLE` 포함된 review 실행 | 저장된 message에 `***REDACTED:<label>***` 치환됨, raw 토큰 0건(`grep -c "AKIA[A-Z0-9]"` = 0) |
| AC-7 | Bash로 `ts1=$(date +%s%3N); ...append...; ts2=$(date +%s%3N); echo $((ts2-ts1))` | 출력값 < 200 |

### Regression

- 기존 review 워크플로(Step 1~6)가 Step 4.7 추가 후에도 정상 동작: Approve 시 `completedSteps` 추가됨, Request Changes 시 추가 안 됨 — Step 6 분기 변경 없음 확인.
