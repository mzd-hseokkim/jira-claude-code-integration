# Design: MAE-170 - [1.1.11] discover --from 모드에 Conflict Detection 추가

## Overview

본 설계는 `jira-task-discover` 스킬에 import 본문(`--from <path>`)과 Step 3 답변 사이의 모순을 자동 감지·격상하는 단계를 추가하기 위한 문서 변경 설계다. 코드 동작은 LLM 추론 가이드(SKILL.md) 변경으로 한정되며 신규 파일 생성·외부 호출·기존 산출물 retrofit은 포함하지 않는다.

- **Plan 참조**: `docs/plan/MAE-170.plan.md`
- **변경 대상 스킬**: `skills/jira-task-discover/SKILL.md`
- **변경 대상 메타**: `.claude-plugin/plugin.json` (version)
- **참고 design**: `docs/design/MAE-168.design.md` (Confirm Gate 인터페이스 슬롯), `docs/design/MAE-169.design.md` (Trace Marker 형식, `*(source: from)*`)

### Decision: Conflict Detection 단계 위치

| 후보 | 위치 | 채택 여부 | 사유 |
|------|------|----------|------|
| Step 3 본문에 통합 (질문 직후) | Step 3 안 | X | Step 3는 "질문/답변" 책임이 명확함. detection은 별도 책임 |
| Step 4 본문에 통합 (합성 직후) | Step 4 안 | X | Step 4는 "합성/마커 부여" 책임이 명확함. 합성 결과 위에 conflict가 또 얹히면 책임이 혼재 |
| **Step 3 종료 ↔ Step 4 진입 사이에 Step 3.5 신규** | 워크플로 | **O** | 단일 책임. Step 3 결과(답변)와 import 본문(Step 0/Step 2 컨텍스트)을 입력으로 받아 Open Questions에 격상할 항목을 산출. Step 4가 합성 시 그 결과를 Open Questions에 자동 포함 |

**결론**: Step 3.5 신규 섹션으로 분리. 이름은 "Step 3.5: Conflict Detection (--from mode only)".

### Decision: Conflict 격상 형식의 단일 출처

| 후보 | 위치 | 채택 여부 | 사유 |
|------|------|----------|------|
| 외부 템플릿 (`templates/requirements.template.md`)에 형식 정의 | 외부 파일 | X | 본 이슈는 SKILL.md만 surgical 편집 |
| SKILL.md Step 3.5 본문에 코드 블록으로 형식 정의 | 워크플로 본문 | **O** | Conflict detection 책임과 형식이 한 곳에서 보임. Step 4 합성 시 동일 파일 내 참조 |

**결론**: 본 이슈가 conflict 격상 형식 표준의 단일 출처(SSOT)다. SKILL.md Step 3.5 본문에 형식을 코드 블록으로 명시하고, Inline Fallback Template Open Questions placeholder에 그 형식의 예시 1개를 추가한다.

### Decision: Conflict 인정 케이스의 경계 (4개 카테고리별)

| 카테고리 | 출처 | conflict 인정 케이스 |
|---------|------|--------------------|
| **Stakeholders (Q1)** | Step 3 답변 1번 | 사용자 그룹 명칭/범위가 명확히 다름 (예: "운영자" vs "일반 사용자") |
| **Goals & Success Criteria (Q2)** | Step 3 답변 2번 | 측정 기준이 상충 (예: "처리량 1k/s" vs "처리량 1만/s"; "응답 200ms" vs "응답 1s") |
| **Constraints (Q3)** | Step 3 답변 3번 | import에 없던 새 제약이 답변으로 등장; import의 기존 제약을 답변이 명시적으로 부정 |
| **Non-functional Requirements (Q4)** | Step 3 답변 4번 | 성능/보안/접근성/관측성 항목이 명시적으로 충돌 (`--lite + --from` 동시 사용 시 Q4 비활성화 → NFR 카테고리 자동 제외) |

**결론**: 비교 대상은 위 4개 카테고리에 한정. FR/Edge Cases/Out of Scope/Open Questions(Step 4 합성 4종)는 본 이슈의 비교 대상이 아니다 (그들은 Step 3.5보다 늦게 합성되며, 합성 자체에 import 본문이 베이스로 들어가므로 별개 책임).

### Decision: Prose 비교 휴리스틱

| 케이스 | 처리 |
|--------|------|
| **명시적으로 다른 결론** | conflict 격상 |
| **단순 추가 정보 (non-contradictory addition)** | conflict 아님 (격상 안 함) |
| **다국어 혼재 (한국어 vs 영어)** | LLM의 의미 단위 비교에 위임. SKILL.md 1줄 노트로 "다국어 비교는 LLM 추론에 의존" 명시 |
| **타이핑 실수 의심 (예: "운영자" vs "운영잔")** | 본 이슈 범위 밖. SKILL.md 1줄 노트로 "타이핑 실수에 의한 false positive는 confirm gate에서 사용자가 수정 가능" 명시 |
| **import 본문 자체가 모순 (PRD 내부 충돌)** | 본 이슈 범위 밖. SKILL.md 1줄 노트로 "import 자체의 품질은 가정" 명시 |

**결론**: 명시적 결론 충돌만 격상. **단순 추가 정보는 false positive를 막기 위해 명시적으로 제외**.

### Decision: 격상 형식 표준

```
- [CONFLICT] <카테고리>: import="<원본>" vs answer="<답변>" — 어느 쪽이 정확한지 결정 필요
```

원칙:
- `<카테고리>`: 4종 중 하나 (Stakeholders / Goals / Constraints / NFR). 풀네임이 너무 길면 약어 허용 (예: NFR)
- `<원본>` / `<답변>`: 한 줄 요약. 원문이 길면 의미가 통하는 짧은 인용. 인용부호(`"..."`) 안에 줄바꿈/이탤릭/볼드는 허용하지 않음 (가독성)
- 마지막 한국어 문구 ("어느 쪽이 정확한지 결정 필요")는 고정. 사용자 결정 대기임을 명시하기 위함

### Decision: Trace Marker와의 상호작용

| 항목 | 처리 |
|------|------|
| `[CONFLICT]` 격상 항목 자체 | trace marker(`*(synthesized)*` 등) **미부착**. `[CONFLICT]` prefix 자체가 출처 표시 역할 |
| import 본문에 이미 부착된 marker (`*(source: from)*` 등) | 비교 시 marker는 무시하고 본문만 비교. 격상 항목에 marker는 옮기지 않음 |

**결론**: `[CONFLICT]` prefix와 trace marker는 **상호 배타**. 한 항목에 둘 다 붙지 않는다. SKILL.md Step 3.5 본문에 1줄 명시.

### Decision: No-op 진입 조건

| 조건 | Step 3.5 진입 |
|------|-------------|
| `--from` 모드 + import 파일 비어있지 않음 | **진입** (정상 케이스) |
| `--from` 모드 + import 파일 비어있음 (Step 0 fallback으로 default 모드 전환됨) | 통과 (Step 0에서 이미 `--from` 효과 무효화) |
| default 모드 (no `--from`) | 통과 (비교할 import 본문 없음) |
| `--lite` 모드 단독 (no `--from`) | 통과 (비교할 import 본문 없음) |
| `--lite + --from` 모드 | **진입** (Q4 비활성화 → NFR 카테고리 자동 제외, 나머지 3 카테고리는 정상 비교) |

**결론**: `--from` 모드 + import 본문 존재일 때만 진입. SKILL.md Step 3.5 시작부에 진입 조건을 명시.

### Decision: Step 4 / Step 4.5와의 협력 인터페이스 (확정)

| 단계 | 협력 인터페이스 |
|------|---------------|
| **Step 4 (Generate Requirements Document)** | Step 3.5에서 격상된 conflict 항목은 Step 4의 Open Questions 섹션에 자동 포함됨. 기존 TBD 항목과 함께 나열 (순서: TBD 항목 먼저, conflict 항목 다음) |
| **Step 4.5 (Synthesis Confirm)** | conflict가 1건 이상 감지되면 Confirm Gate의 합성 결과 요약보다 **먼저** "Conflict Detection 결과" 섹션을 표시. 표시 형식: 격상된 `[CONFLICT]` 항목들의 bullet 목록 (요약 표시 규칙 동일: 4건 이상 시 상위 3개 + "외 N건") |

**결론**: Step 4.5 L204의 "예약 문구" 줄을 다음과 같이 갱신:

> **모두(冒頭) — Conflict Detection 결과 표시:** Step 3.5에서 감지된 `[CONFLICT]` 항목이 1건 이상이면 합성 결과 요약보다 **먼저** "Conflict Detection 결과" 섹션을 표시한다 (3건 이내, 4건 이상 시 상위 3개 + "외 N건" 축약). 사용자는 이 섹션을 검토 후 `proceed`/`revise`/`cancel` 결정을 내린다. conflict 0건이면 본 섹션은 표시하지 않는다.

## Sequence Diagram

```mermaid
sequenceDiagram
    participant User
    participant Discover as jira-task-discover
    participant FS as File System
    participant Doc as docs/requirements/&lt;slug&gt;.requirements.md

    User->>Discover: /jira-task discover "<topic>" --from <path>
    Note over Discover: Step 0: Parse arguments<br/>--from path 검증
    Discover->>FS: Read import 파일
    FS-->>Discover: import 본문 (또는 빈 파일 fallback)

    Note over Discover: Step 2: Codebase Context Collection<br/>(import 본문 + 코드 발췌)

    Note over Discover: Step 3: Batched Questions<br/>(누락 카테고리만 선별 질문)
    Discover->>User: AskUserQuestion (필요한 카테고리만)
    User-->>Discover: 답변

    Note over Discover: Step 3.5: Conflict Detection (신규)
    alt --from 모드 + import 비어있지 않음
        loop 4 카테고리 (Stakeholders/Goals/Constraints/NFR)
            Discover->>Discover: import 본문 vs 답변 비교
            alt 명시적 결론 충돌
                Discover->>Discover: [CONFLICT] 항목 생성
            else 단순 추가 정보 또는 동일
                Discover->>Discover: 격상 안 함
            end
        end
    else 그 외 모드
        Discover->>Discover: Step 3.5 통째로 건너뜀
    end

    Note over Discover: Step 4: Generate Requirements Document<br/>(Open Questions에 [CONFLICT] 자동 포함)
    Discover->>Discover: 합성 4종 (FR/Edge/OOS/OQ) 생성<br/>OQ에 conflict 항목 자동 포함

    Note over Discover: Step 4.5: Synthesis Confirm
    alt conflict ≥ 1건
        Discover->>User: "Conflict Detection 결과" 섹션 (먼저 표시)
    end
    Discover->>User: 합성 결과 요약 + AskUserQuestion (proceed/revise/cancel)
    User-->>Discover: 결정

    alt proceed
        Discover->>Doc: Write
        Doc-->>User: requirements 문서 (Open Questions에 [CONFLICT] 포함)
    else revise / cancel
        Note over Discover: 기존 Step 4.5 분기 처리 그대로
    end
```

핵심 변경점:
- Step 3과 Step 4 사이에 Step 3.5 신규 추가 (conflict detection)
- Step 4 Open Questions 합성 시 Step 3.5 격상 항목 자동 포함
- Step 4.5 모두(冒頭)에 conflict 결과 표시 (1건 이상 있을 때만)

## Interfaces / Types

본 이슈는 코드 변경이 없으므로 타입/인터페이스 정의는 마크다운 텍스트 형식만 명시한다.

| 이름 | 역할 |
|------|------|
| `[CONFLICT]` prefix | Open Questions 섹션 항목 시작에 붙는 격상 표지. trace marker와 상호 배타 |
| `[CONFLICT] <카테고리>: import="<원본>" vs answer="<답변>" — 어느 쪽이 정확한지 결정 필요` | 격상 형식 표준 (단일 줄, prefix 포함) |
| `<카테고리>` | 4종 중 하나: `Stakeholders` / `Goals` / `Constraints` / `NFR` (`Goals` 또는 `Goals & Success Criteria`, `NFR` 또는 `Non-functional Requirements` 약어 허용) |
| `<원본>` / `<답변>` | 한 줄 요약 (인용부호 안에 줄바꿈/이탤릭/볼드 금지). 원문 길면 의미가 통하는 짧은 인용 |
| Step 3.5 진입 조건 | `--from` 모드 + import 파일 비어있지 않음 |
| Step 3.5 No-op 조건 | default / `--lite` 단독 모드 또는 import 파일이 빈 파일이어서 default fallback된 경우 |
| Step 4 협력 슬롯 | Open Questions 섹션에 `[CONFLICT]` 항목 자동 포함 (기존 TBD 항목과 함께) |
| Step 4.5 협력 슬롯 | Confirm Gate 모두(冒頭)에 "Conflict Detection 결과" 섹션 표시 (1건 이상 시) |

## Error Handling

| 시나리오 | 처리 전략 |
|---------|----------|
| `--from` 파일이 빈 파일 (Step 0 fallback) | Step 3.5 통째로 건너뜀. 자연 처리 (No-op 조건 명시). 별도 경고 없음 |
| `--from` 모드에서 import 본문에 4 카테고리가 모두 있고 답변 0건 | Step 3 자체가 호출되지 않으므로 비교 대상 없음. Step 3.5 통과(0건). 자연 처리 |
| 한 카테고리에 conflict 다수 | 각각 별도 `[CONFLICT]` 항목으로 격상 (멀티 conflict 허용). 같은 카테고리 묶기 없음 |
| 다국어 혼재 (import 한국어, 답변 영어) | LLM의 의미 단위 비교에 의존. SKILL.md 1줄 노트로 명시 ("LLM 추론에 의존") |
| 타이핑 실수에 의한 false positive | 본 이슈 범위 밖. SKILL.md 1줄 노트로 "사용자가 confirm gate에서 수정 가능" 명시 |
| import 본문 자체에 내부 모순 | 본 이슈 범위 밖. SKILL.md 1줄 노트로 "import 자체의 품질은 가정" 명시 |
| LLM이 단순 추가 정보를 conflict로 오인식 | SKILL.md prose 휴리스틱에 "**명시적으로 다른 결론일 때만**" 강조. 명시 케이스(단순 추가 = 격상 안 함)로 LLM 추론 가이드 |
| `[CONFLICT]` 형식이 너무 길어 가독성 저하 | `<원본>` / `<답변>`을 한 줄 요약으로 강제. 원문 길면 의미 통하는 짧은 인용 사용. SKILL.md 형식 표준에 명시 |
| Step 4.5 Confirm Gate에서 conflict + 합성 요약 혼재로 사용자 혼란 | conflict를 합성 요약보다 **먼저** 분리 표시. SKILL.md L204 갱신으로 명시 |
| import 본문에 이미 trace marker 부착된 항목 | 비교 시 marker 무시하고 본문만 비교. 격상 항목에는 marker 미부착 (`[CONFLICT]` prefix가 출처 표시) |
| `--lite + --from` 동시 사용 | Q4(NFR) 비활성화 → NFR 카테고리 자동 제외 (3 카테고리만 비교). SKILL.md Step 3.5에 1줄 노트 |
| Conflict 0건일 때 Step 4.5 표시 | 자연 통과 (조용히 합성 요약만 표시). SKILL.md L204 갱신에 명시 |
| `.claude-plugin/plugin.json` version 증가 누락 | impl 단계 체크리스트 + test 단계 검증 |

## Security Checklist

본 이슈는 외부 API/네트워크 호출이 없고, 입력은 LLM 컨텍스트 내 텍스트로 한정되므로 보안 위협 표면이 좁다. 그래도 import 본문과 답변이 격상 항목에 인용되어 산출 문서로 노출될 수 있으므로 다음을 점검한다.

- [ ] **민감 정보 인용**: `import="<원본>"` 또는 `answer="<답변>"`에 토큰/비밀번호/PII가 포함될 가능성. SKILL.md Step 3.5에 "원문 인용 시 민감 정보 제외 (있으면 redact)" 1줄 가이드 추가 검토 (test 단계 sanity check 항목)
- [ ] **import 본문 신뢰 경계**: import 파일은 사용자가 명시적으로 제공한 것이므로 신뢰. 단 `--from` 경로 traversal 방지는 기존 SKILL.md L60-68 처리에 위임 (본 이슈로 새 위협 추가 없음)
- [ ] **사용자 답변 sanitize**: 답변은 LLM이 받아 처리. 격상 항목에 답변 본문이 들어가도 산출물은 로컬 .md 파일이라 실행 위험 없음. Markdown injection은 격상 형식 표준이 인용부호로 감싸서 영역 제한
- [ ] **격상 항목의 Jira 노출**: requirements 문서가 후속 jira-task-create로 Jira에 첨부될 수 있음. import 본문이나 답변에 자격증명·내부 URL이 들어 있으면 Jira에 노출. 본 이슈는 새 위협을 추가하지 않으나(기존에도 답변/import는 이미 노출됨), 격상 항목은 추가 노출 표면. SKILL.md Step 3.5 보안 가이드에 "민감 정보 redact" 1줄 추가 권장
- [ ] **plugin.json version**: 잘못된 형식(non-semver) 입력 방지. 단순 patch+1이라 위험 낮음

## Test Plan

본 이슈는 코드가 아닌 SKILL.md(LLM 가이드) 변경이므로 자동 unit test 작성은 어렵다. 대신 `/jira-task test` 단계에서 다음을 명세 단위로 수행한다.

### Test Type Scope

- **Unit test**: 해당 없음 (코드 산출물 없음)
- **Document inspection**: SKILL.md/plugin.json/Inline Fallback Template diff에 대한 grep/시각 검증
- **Dry-run sanity check**: discover 스킬을 `--from` 모드 sample input으로 가상 호출하여 conflict 감지·격상 일관성 확인

### Test Case Specifications

#### TC-1: SKILL.md에 Step 3.5 섹션이 신규 추가됨 (AC-1)
- 검증 방법: grep으로 SKILL.md에 `Step 3.5` 또는 `Conflict Detection` 헤딩 존재 확인. 위치가 Step 3 종료(`### Step 3:` 다음)와 Step 4 진입(`### Step 4:` 이전) 사이임을 확인 (line 번호 검증)
- 기대 결과: `### Step 3.5:` 헤딩이 Step 3과 Step 4 사이에 존재
- 경계 조건: 헤딩 텍스트는 정확히 매칭 안 해도 의미 통하면 OK (예: `### Step 3.5: Conflict Detection (--from mode only)`)

#### TC-2: 4 카테고리별 비교 규칙 명시 (AC-2)

  4. `NFR` 또는 `Non-functional` 또는 `Q4`

- 경계 조건: 표 또는 bullet 어느 쪽이든 인정. 카테고리별 conflict 인정 케이스가 본문 또는 표에 명시되어 있어야 함
