## Background

### 현재 상황

`skills/jira-task-discover/SKILL.md`의 `--from <path>` 모드는 기존 요구사항 문서를 import한 뒤 Step 3에서 "**누락된 카테고리만 선별 질문**"하도록 설계되어 있다 (L119: "Step 2에서 import한 기존 문서를 분석해 누락된 카테고리만 선별 질문한다"). 즉, import한 문서에 이미 있는 항목은 다시 묻지 않는다.

또한 Step 4.5(Confirm Gate)는 MAE-168을 통해 도입되었고, L204에 다음 문장이 박혀 있다:

> "**모두(冒頭) — 협력 인터페이스:** Conflict Detection 결과(MAE-170)가 존재하면 합성 결과 요약보다 **먼저** 표시한다. 본 태스크 범위에서는 인터페이스 슬롯만 예약하며, 실제 conflict 데이터 수집·표시는 MAE-170 머지 후 후속 PR로 처리한다."

→ **본 이슈가 채워야 할 슬롯이 이미 예약되어 있는 상태.**

### 문제

`--from`이 "선별 질문"만 한다면 import 본문과 답변 사이의 모순은 발생하지 않을 것 같지만, 실제로는 다음 시나리오에서 충돌이 생긴다.

- 사용자가 "Other → 자유 입력"으로 import 본문과 다른 답을 적는 경우 (선별 질문이라도 사용자가 이미 답변된 카테고리에 대해 추가 의견을 적을 여지가 있음)
- import한 PRD에 "주 사용자: 운영자"로 적혀 있는데, NFR 질문(`Q4`)의 자유 답변에서 사용자가 "일반 사용자도 사용한다"라고 부수적으로 언급
- import 본문이 오래되어 현재 사용자 답변과 사실상 모순되는 경우

→ **현재 워크플로는 어느 쪽이 우선인지 규칙 없음**. LLM이 임의로 한쪽을 채택하면 사후 검증 불가능. 잘못된 정보가 자동으로 합성 결과에 들어가 후속 `jira-task-create`로 전달될 위험.

### 해결 방향

import 본문과 답변 사이의 모순을 **자동 감지**하여 `Open Questions` 섹션에 `[CONFLICT]` 형식으로 격상한다. 이러면 다음 효과가 생긴다.

1. LLM이 임의로 한쪽을 채택하지 않고, **사용자 결정 대기**로 명시
2. Step 4.5 Confirm Gate에서 "Conflict Detection 결과"로 우선 표시되어 사용자가 즉시 인지
3. 후속 `jira-task-create`에서 Open Questions로 보존되어, Jira 이슈 생성 시 결정 보류 상태로 추적 가능

### 영향도

discover 스킬은 후속 `jira-task-create`가 그대로 Jira 이슈로 변환하는 입력이다. `--from` 모드는 PO/PM이 이미 작성한 PRD를 입력으로 받는 시나리오를 위한 것이라, **legacy 문서와 새 답변의 모순**이 가장 자주 발생할 가능성이 큰 모드다. 따라서 conflict detection은 `--from` 모드의 신뢰성을 사후 검증 가능하게 만드는 핵심 인프라이며, MAE-168(Confirm Gate)·MAE-169(Trace Marker)와 함께 1.1 phase 품질 강화 묶음의 마지막 축이다.

## Scope

### In Scope

- `skills/jira-task-discover/SKILL.md` 워크플로 surgical 편집:
  1. **Step 3.5 신규 섹션 추가** (Step 3 종료 ↔ Step 4 진입 사이): "Conflict Detection (--from mode only)"
  2. **4개 카테고리별 비교 규칙** 명시:
     - Stakeholders: 사용자 그룹 명칭/범위가 명확히 다른지
     - Goals & Success Criteria: 측정 기준이 상충하는지 (예: "처리량 1k/s" vs "처리량 1만/s")
     - Constraints: import에 없던 새 제약이 답변으로 등장하거나, import의 기존 제약을 답변이 명시적으로 부정하는지
     - NFR: 성능/보안/접근성/관측성 항목이 명시적으로 충돌하는지
  3. **Prose가 긴 항목의 비교 휴리스틱** 명시:
     - 자유 입력(Other → 자유 텍스트)의 경우 키워드 또는 의미 단위로 비교
     - 단순 추가 정보(non-contradictory addition)는 conflict가 아님 — 명시적으로 다른 결론일 때만 격상
  4. **격상 형식 표준** 명시: `- [CONFLICT] <카테고리>: import="<원본>" vs answer="<답변>" — 어느 쪽이 정확한지 결정 필요`
  5. **No-op 조건 명시**:
     - `--from` 모드가 아닐 때는 Step 3.5 통째로 건너뛰어짐
     - import 파일이 빈 파일일 때(L68 "default 모드로 fallback")도 Step 3.5 건너뛰어짐
  6. **Step 4 / Step 4.5와의 협력 인터페이스 갱신**:
     - Step 4: 감지된 conflict는 Open Questions 섹션에 `[CONFLICT]` prefix로 자동 격상 (기존 Open Questions 항목과 함께)
     - Step 4.5 L204의 "인터페이스 슬롯 예약 문구"를 실제 동작 명세로 갱신 (conflict가 있으면 합성 요약보다 먼저 conflict 목록 표시)
- **Inline Fallback Template Open Questions 섹션**의 placeholder 예시에 `[CONFLICT]` 케이스 1개 추가
- `.claude-plugin/plugin.json` version 증가 (CLAUDE.md 규칙)

| `--from` 빈 파일 fallback 케이스(L68)에서 Step 3.5가 잘못 실행되는 회귀 | Medium | AC-5에 명시. impl 시 fallback 분기에서 Step 3.5 건너뛰는 가드 명시 |
| 사용자가 자유 입력 답변에서 타이핑 실수(예: "운영자"→"운영잔")로 LLM이 conflict로 오인 | Low | 본 이슈 범위 밖. SKILL.md에 한 줄 노트로 "타이핑 실수에 의한 false positive는 사용자가 confirm gate에서 수정 가능"이라고 명시 가능 |
| `.claude-plugin/plugin.json` version 누락 | Medium | Task #10에 명시. impl 단계 체크리스트로 운영 |

## Edge Cases

- **import 본문이 정확히 답변과 동일**: conflict 0건 → Step 3.5는 조용히 통과 → Open Questions 섹션은 기존 TBD 항목만으로 구성 (격상 없음). 사용자에게 별도 안내 없음.
- **import 본문에 4개 카테고리 모두 있고, 답변이 0건 (`--from` 모드에서 누락 카테고리 0)**: Step 3 자체가 호출 안 됨. Step 3.5도 비교할 답변이 없으므로 conflict 0건. 이 케이스는 자연스러우므로 별도 처리 불필요.
- **하나의 카테고리에 conflict가 여러 개**: 각각 별도 `[CONFLICT]` 항목으로 격상 (멀티 conflict 허용). 같은 카테고리 묶기는 하지 않음.
- **import 본문이 한국어, 답변이 영어** (또는 반대): LLM의 의미 단위 비교에 의존 — 본 이슈는 형식만 정의, 비교 정확도는 LLM에 위임. SKILL.md에 1줄 노트로 "다국어 비교는 LLM 추론에 의존" 가능.
- **import 본문에 trace marker(`*(source: from)*`)가 이미 붙어 있음**: 비교 시 marker는 무시하고 본문만 비교. conflict 격상 시에는 marker 미부착.
- **`[CONFLICT]` prefix가 격상 항목 자체의 일부가 되어 trace marker(`*(synthesized)*` 등)와 충돌**: `[CONFLICT]`는 prefix 역할로 충돌 표지이므로 trace marker는 부착하지 않는다. 명시적으로 SKILL.md에 1줄 노트.
- **모든 답변이 "Other → (빈)" + `--from` 모드**: 답변이 모두 `TBD`이므로 conflict 비교 의미 없음. Step 3.5는 통과(0건). 자연스러운 동작.
- **`--from` 파일이 1MB 초과**: SKILL.md L67에 confirm 단계가 있으므로 이미 사용자가 진행 의사를 확인. 본 이슈 추가 처리 없음.
- **import 본문 자체에 conflict가 있음** (예: PRD 내부에서 "주 사용자: 운영자"와 "주 사용자: 일반 사용자"가 둘 다 있음): 본 이슈 범위 밖. SKILL.md 1줄 노트로 "import 본문 내부 모순은 본 이슈 범위 밖, import 자체의 품질 가정"이라고 명시.

```markdown
### Step 3.5: Conflict Detection (--from mode only)

`--from` 모드에서 import 본문과 Step 3 답변 사이의 모순을 자동 감지하여 Open Questions로 격상한다. 이는 후속 jira-task-create로 잘못된 정보가 전달되는 것을 차단한다.

- `--from` 모드 (default / `--lite` 단독에서는 통째로 건너뜀)
- import 파일이 비어 있지 않음 (빈 파일 fallback 케이스(Step 0)에서는 default 모드로 전환되므로 자연스럽게 건너뜀)

| Non-functional Requirements (Q4) | 성능/보안/접근성/관측성 항목이 명시적으로 충돌 (`--lite + --from` 동시 사용 시 Q4 비활성화 → NFR 카테고리 자동 제외) |

**Prose 비교 휴리스틱:**
- 키워드 또는 의미 단위로 비교 (의미 단위 비교는 LLM 추론에 의존)

```

```

**Trace Marker 처리:**
- `[CONFLICT]` prefix 자체가 출처 표시 역할을 하므로 별도 trace marker(MAE-169) 미부착

**Step 4와의 협력:**
```
