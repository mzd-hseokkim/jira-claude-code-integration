## Acceptance Criteria

### AC-1: JSON 스키마 필수 필드 문서화
- **Given**: `docs/review-log/` 디렉터리가 존재하고 스키마 문서가 생성됨
- **When**: 스키마 문서를 열람할 때
- **Then**: 필수 필드(`taskId`, `timestamp`, `reviewerVersion`, `outcome`, `findings[]`, `severityCounts`, `falsePositive`, `userOverride`)가 모두 명시되고, `findings[]` 항목 스키마(`id, severity, file, line, category, message`)도 포함됨

### AC-2: redact 정규식 셋 정의
- **Given**: redact 정책 모듈(또는 문서)이 존재함
- **When**: API key, Bearer token, credential 패턴을 포함한 민감정보 샘플을 입력할 때
- **Then**: 정의된 정규식 셋이 해당 패턴을 모두 매칭하며, 대응 단위 테스트가 통과함

### AC-3: 민감정보 0건 저장 검증
- **Given**: redact 로직이 정의된 단위 테스트 환경
- **When**: 민감정보(API key, token, credential)가 포함된 데이터를 로그 변환 처리할 때
- **Then**: 변환 결과에 민감정보가 0건 포함되며 단위 테스트로 검증됨

## Scope Decisions

| # | 결정 | 대안 | 선택 이유 | 영향 |
|---|---|---|---|---|
| 1 | 스키마는 코드 구현 없이 문서(Markdown) + 정규식 모듈로만 정의 | JSON Schema 파일(.json) + 검증 라이브러리 | Story 1은 정의/문서화 단계이며, Story 2에서 실제 append 구현 시 스키마를 참조. 과도한 사전 구현 방지 | 구현 부담 최소화; Story 2에서 확장 가능 |
| 2 | redact 정규식은 Python 표준 라이브러리(`re` 모듈)만 사용 | 외부 라이브러리(예: scrubadub, presidio) | Epic 제약: Python 표준 라이브러리만, macOS/Linux/Windows 호환 필요 | 이식성 보장, 의존성 없음 |
| 3 | 단위 테스트는 Python 표준 `unittest` 또는 `pytest` 사용 (둘 다 macOS/Linux/Windows 호환) | 별도 테스트 프레임워크 | 표준 라이브러리 제약과 호환, CI 통합 용이 | 추가 의존성 없음 |

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| redact 정규식이 일부 credential 패턴을 누락 | 민감정보 유출 가능성 | 정규식 셋을 충분히 넓게 정의하고, 경계 케이스(빈값, 짧은 토큰 등) 단위 테스트 포함 |
| Story 2/3에서 스키마 변경 요청 발생 | Story 1 산출물 재작업 | 스키마 문서에 version 필드 포함 및 변경 이력 관리. Story 2 시작 전 리뷰 |
| Python 표준 라이브러리만으로 복잡한 credential 패턴 커버 불가 | redact 품질 저하 | 사전 패턴 목록 정리 후 Epic 담당자와 리뷰. 누락 패턴은 Open Items로 이월 |
