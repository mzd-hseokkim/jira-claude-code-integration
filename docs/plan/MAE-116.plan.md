# Plan: MAE-116 — [1.1.3] jira-task-create와의 연결 (--from-requirements)

## Background

부모 에픽 MAE-104(Phase 1.1)는 `discover → create → init → start → plan → ...`로 확장되는 신규 워크플로 도입을 목표로 한다. 형제 서브태스크 진행 현황은 다음과 같다:

- ✅ MAE-115: `jira-task-discover` 스킬 작성 (요구사항 문서 + 이슈 분해 제안 산출)
- ✅ MAE-117: `templates/requirements.template.md` 생성
- ✅ MAE-118: `completedSteps`에 `"discover"`, `"create"` 추가
- ✅ MAE-119: `commands/jira-task.md` 라우팅에 `discover` 액션 추가
- 🔄 **MAE-116 (본 태스크): `jira-task-create`와의 연결 — `--from-requirements` 분기 추가**
- ⏳ MAE-120, MAE-121: 문서 갱신 (CLAUDE.md, README)

본 태스크는 **`discover` 산출물(`docs/requirements/<TOPIC-SLUG>.requirements.md`)을 입력으로 받아 에픽/스토리/서브태스크를 일괄 등록하는 자동화 분기**를 `jira-task-create` 스킬에 추가한다. 이 매듭이 닫히면 `/jira-task discover "<주제>"` → `/jira-task create --from-requirements <경로>` 파이프가 end-to-end로 동작한다.

핵심 입력은 `discover`가 문서 끝에 추가하는 **`Proposed Issue Breakdown`** 섹션이다. 형식:

```markdown
## Proposed Issue Breakdown

- **Epic**: <에픽 1줄 요약>
  - **Story 1**: <스토리 요약>
    - Sub-task 1.1: <서브태스크 요약>
    - Sub-task 1.2: <서브태스크 요약>
  - **Story 2**: <스토리 요약>
    - Sub-task 2.1: <서브태스크 요약>
```

이 트리를 파싱해서 `jira-task-create`의 기존 생성/링크 로직(Step 6-1 ~ 6-4)을 재사용한다.

## Scope

### In Scope

- `skills/jira-task-create/SKILL.md`에 `--from-requirements <경로>` 분기 추가
  - `$ARGUMENTS` 파싱 규칙 확장: `--from-requirements <path>` 토큰 인식 (Step 0)
  - 새 Step (예: Step 1.5 `Parse Requirements Document`): 요구사항 문서를 읽어 `Proposed Issue Breakdown` 섹션 추출 + 트리 파싱
  - Step 3/4(서브태스크 판단/제안)를 import 모드에서는 **skip**하고, 파싱된 트리를 그대로 초안으로 채택
  - Step 5(Final Preview)에서 import 출처 명시 후 사용자 confirm 받음
  - Step 6(Create in Jira) 로직은 그대로 재사용
- 트리 → 이슈 등록 매핑 규칙 정의:
  - `Epic` → `issue_type: "Epic"` (단, 프로젝트가 Epic 비활성 시 `Task` + label로 폴백)
  - `Story` → `issue_type: "Story"` (Epic을 parent로 연결)
  - `Sub-task` → `issue_type: "Subtask"` (Story를 parent로 연결)
  - 같은 부모 아래 서브태스크/스토리는 기본 병렬, `(blocks: ...)` 표기가 있으면 `Blocks` 링크 등록
- `discover` 완료 직후 안내(Step 6 Completion Summary)에 `--from-requirements` 사용 명령이 이미 표시됨 — 이 약속을 깨지 않도록 인자 형식을 그대로 수용
- 파일 부재/형식 오류/빈 트리 등 에러 처리 명세
- 인자 충돌 정의: `--from-requirements`와 `$ARGUMENTS`의 자연어 힌트가 동시에 있으면 import를 우선 (자연어 힌트는 description 보강용)
- `commands/jira-task.md`의 `create` 라우팅 검토: `--from-requirements`는 별도 분기가 아니라 `args` 그대로 위임으로 충분(이미 `<사용자가 입력한 create 이후의 전체 인자를 그대로 전달>` 규약). 변경 불필요 확인
- smoke 테스트: 견본 요구사항 문서 1건을 만들어 파싱·생성·링크 흐름이 SKILL.md 명세대로 동작하는지 수기 시뮬레이션 (실제 Jira 호출은 design/impl 단계에서)
- `.claude-plugin/plugin.json`의 `version` 증가

### Out of Scope

- `jira-task-discover` 스킬 자체의 수정 (MAE-115 범위)
- `templates/requirements.template.md` 형식 변경 (MAE-117 범위)
- `completedSteps` 유효 단계 변경 (MAE-118 범위)
- `commands/jira-task.md`에 새로운 액션 추가 (MAE-119가 `discover`만 추가; `create --from-requirements`는 기존 `create` 분기로 흡수됨)
- CLAUDE.md / README 문서 갱신 (MAE-120, MAE-121)
- `docs/requirements/INDEX.md` 등 인덱스 파일 자동 관리
- 사용자가 임의 형식으로 작성한 요구사항 문서의 자동 변환 (본 태스크는 `discover`가 산출한 표준 트리 형식만 지원)
- Bulk import용 별도 CLI/스크립트 분리 (현재는 스킬 내부 분기로만 처리)
- Jira batch API 사용 (`jira_batch_create_issues`는 SKILL.md에 명시된 사용 금지 규칙 유지)

## Acceptance Criteria

### AC-1: `--from-requirements <path>` 분기 동작 명세

- Given: `skills/jira-task-create/SKILL.md`가 갱신됨
- When: 사용자가 `/jira-task create --from-requirements docs/requirements/sample.requirements.md` 실행
- Then: SKILL.md가 (1) `--from-requirements` 토큰을 Step 0에서 파싱, (2) 파일 존재/`Proposed Issue Breakdown` 섹션 존재 검증, (3) 트리를 파싱해 Epic/Story/Sub-task 초안으로 채택, (4) 사용자 confirm 후 Jira에 일괄 생성하도록 명시되어야 한다

### AC-2: 트리 → 이슈 매핑 규칙 명시

- Given: SKILL.md에 매핑 규칙 표가 추가됨
- When: 트리에서 Epic 1 + Story N + Sub-task M이 파싱됨
- Then: SKILL.md가 (1) Epic을 먼저 생성, (2) Story들을 Epic을 parent로 묶어 생성, (3) Sub-task들을 각자의 Story를 parent로 묶어 생성, (4) `(blocks: ...)` 표기를 `Blocks` 이슈 링크로 변환하도록 명시되어야 한다

### AC-3: discover 안내 메시지와의 정합성

- Given: MAE-115의 `jira-task-discover/SKILL.md` Step 6 Completion Summary가 다음 명령을 노출:
  `Next: /jira-task create --from-requirements docs/requirements/<slug>.requirements.md`
- When: 사용자가 안내 그대로 명령을 실행
- Then: `jira-task-create/SKILL.md`가 같은 인자 형식을 인식하고 처리해야 한다 (안내가 깨지지 않음)

### AC-4: import 모드에서 자동 분해 판단 skip

- Given: `--from-requirements` 모드가 활성화됨
- When: 트리가 정상적으로 파싱됨
- Then: SKILL.md가 Step 3(서브태스크 분해 자동 판단)·Step 4(초안 제안)를 skip하고, 파싱된 트리를 곧바로 Step 5(Final Preview)로 넘기도록 명시되어야 한다

### AC-5: 에러 처리 명세

- Given: SKILL.md에 Error Handling 섹션이 갱신됨
- When/Then: 다음 시나리오 모두 처리 흐름이 명시되어야 한다
  - `--from-requirements`만 있고 경로 누락 → 사용자에게 경로 요청
  - 지정 경로의 파일 부재 → 에러 메시지 + 종료
  - 파일은 있으나 `Proposed Issue Breakdown` 섹션 없음 → 에러 메시지 + 종료 (또는 자연어 모드로 폴백 제안)
  - 트리는 있으나 Epic 노드 없음/Story 0개 → 사용자에게 보강 입력 요청 또는 종료
  - 동일 summary의 이슈가 이미 존재하면 경고 (자동 중복 방지는 안 하되 사용자에게 confirm)

### AC-6: 인자 충돌 처리

- Given: `--from-requirements`와 자연어 힌트가 동시에 전달됨
- When: 둘 다 비어 있지 않은 경우
- Then: import를 우선하고, 자연어 힌트는 Epic description의 추가 컨텍스트로만 사용하도록 명시되어야 한다 (서브태스크 분해 자동 판단으로 회귀하지 않는다)

### AC-7: plugin version 증가

- Given: 본 변경이 `skills/jira-task-create/SKILL.md`를 수정함
- When: 변경 커밋 직전
- Then: `.claude-plugin/plugin.json`의 `version`이 직전 릴리스(현재 0.14.0)에서 한 단계 증가 (예: `0.14.1` 또는 `0.15.0`)

## Edge Cases

- **`--from-requirements` 인자 누락(`--from-requirements`만 있음)**: 사용자에게 경로 요청 (AskUserQuestion) 또는 에러 종료
- **상대 경로 vs 절대 경로**: 둘 다 허용. 상대 경로는 worktree/repo root 기준
- **파일은 있으나 빈 파일**: 에러 종료
- **`Proposed Issue Breakdown` 섹션은 있으나 트리 노드 0개**: 에러 메시지 + 자연어 모드로 폴백 제안
- **Epic 노드 없이 Story부터 시작**: 기본 Epic 1개를 자동 생성 (summary는 파일명 또는 토픽 추론) — 또는 사용자에게 confirm
- **Sub-task가 Story 없이 Epic 직속**: 허용. Story 단계를 비우고 Sub-task를 Epic의 직접 child로 등록 (Subtask는 일반적으로 parent가 Story지만, 프로젝트에 따라 Epic 직속도 허용됨 — fallback 규칙 명시)
- **동일 summary의 이슈가 이미 존재**: 경고 표시, 사용자 confirm 후 진행 (자동 차단은 안 함)
- **트리 들여쓰기 변형 (2/4-space)**: 둘 다 허용
- **불릿 기호 변형 (`-`, `*`)**: 둘 다 허용
- **`(blocks: ...)` 표기에서 존재하지 않는 키 참조**: 에러 출력 후 해당 링크만 skip, 나머지는 진행
- **요구사항 문서가 1MB 초과**: confirm 후 진행 (discover와 동일 패턴)
- **사용자가 Final Preview에서 "취소" 선택**: 아무 이슈도 만들지 않고 종료
- **사용자가 Final Preview에서 "수정" 선택**: 어느 단계로 돌아갈지 질문 (트리 재파싱 / 자연어 모드 전환 / 자유 편집)
- **discover에서 만든 슬러그와 다른 파일명**: 파일명은 자유. import는 경로만 요구

## Open Questions

plan 단계에서 결정 필요한 질문 — design 단계에서 최종 결론:

1. `Proposed Issue Breakdown` 트리 파싱 규칙을 정규식 기반으로 할지, 줄별 들여쓰기/불릿 기반 상태머신으로 할지 (정규식이 단순하지만 변형에 약함)
2. Epic 타입 미지원 프로젝트에서의 폴백 라벨 이름 (`epic-substitute` vs `epic-as-task` 등)
3. `(blocks: ...)` 표기 외에 의존성 표현 변형 허용 여부 (예: `(after: ...)`, `(needs: ...)`) — 일단 `blocks` 단일 키워드로 한정 권장
