## Background

### 현재 상황

`skills/jira-task-design/SKILL.md`의 Step 3 "Generate Design Document"는 design 문서 산출물에 다음 6개 섹션만 명시한다.

1. Architecture (관련 컴포넌트/모듈 구조)
2. Sequence Diagram (Mermaid)
3. Implementation Plan (파일별 변경 요약)
4. Error Handling
5. Security Checklist
6. Test Plan

### 문제

design 단계는 "앞으로 어떻게 만들지의 합의서"인데, **Data Model**(데이터 모델링) 합의가 빠져 있다. 결과적으로:

- DB 스키마 변경, 새 엔티티/테이블 추가가 design 합의 없이 impl에서 사실상 결정됨
- 마이그레이션 전략, 인덱스, 외래 키, 무결성 제약(unique/NOT NULL/check)이 누락되기 쉬움
- API 페이로드/DTO 구조가 코딩 단계에서 즉흥적으로 결정됨
- 캐시/세션 등 in-memory 데이터 구조도 동일 문제

impl/test 단계에서 데이터 누락 이슈를 발견하면 되돌리는 비용이 크다. design 단계에서 잡는 것이 비용 효율적이다.

### 영향도

design 단계는 **다른 모든 후속 task의 design 품질에 영향이 큰 인프라성 변경**이다. 한 번 박아 두면 향후 모든 task의 design 문서에 데이터 모델 합의가 자동으로 들어간다.

## Scope

### In Scope

- `skills/jira-task-design/SKILL.md` Step 3 "Generate Design Document"의 산출물 섹션 명세에 **Data Model** 항목 추가
- Data Model 섹션 위치 명시: **Architecture 다음, Sequence Diagram 앞** (컴포넌트 구조 → 데이터 모델 → 플로우 순)
- Data Model 섹션 권장 하위 항목 6종 가이드:
  1. 새/변경되는 엔티티 (속성 · 타입 · 제약 · 관계)
  2. DB 스키마 (테이블/컬럼/인덱스/FK/마이그레이션 전략)
  3. API 페이로드 (요청/응답 DTO 구조 — 시그니처 수준)
  4. 도메인 객체 (핵심 entity / value object 구조)
  5. 상태 모델 (상태 전이 다이어그램, 해당 시)
  6. 데이터 흐름 (source → transform → sink, 해당 시)
- 데이터 변경이 없는 task에 대한 fallback 가이드: `"N/A — no data changes"` 한 줄 처리 명시
- design 단계 출력 예시 또는 Jira 코멘트 예시 업데이트 (변경 필요 시)

### Out of Scope

- 다른 단계(plan/test/review) 템플릿 정비 → Phase 1.3 / MAE-106 영역
- 기존 design 문서 retrofit (이전에 생성된 design 문서는 그대로 둠)
- 별도 `templates/design.template.md` 파일 신규 생성 → 현재 SKILL.md 인라인 명세 방식 유지 (필요 시 후속 결정)
- design 스킬 다른 Step(1, 2, 4, 4.5, 5) 변경
- 코드 레벨 데이터 모델 검증 자동화 (lint/CI 등)

## Acceptance Criteria

### AC-1: Data Model 섹션이 명시됨
- Given: 사용자가 `skills/jira-task-design/SKILL.md`를 연다
- When: Step 3 "Generate Design Document"의 산출물 섹션 목록을 확인한다
- Then: "Data Model" 섹션이 명시 항목으로 노출된다

### AC-2: 섹션 위치가 명시되어 있다
- Given: SKILL.md Step 3
- When: 산출물 섹션 순서를 본다
- Then: Data Model이 **Architecture 다음, Sequence Diagram 앞** 위치에 박혀 있다

### AC-3: 권장 하위 항목 6종이 가이드로 노출됨
- Given: SKILL.md Step 3 Data Model 섹션
- When: 가이드 문구를 읽는다
- Then: 엔티티 / DB 스키마 / API DTO / 도메인 객체 / 상태 모델 / 데이터 흐름 6종이 모두 가이드로 명시됨

### AC-4: 데이터 변경 없는 task용 fallback이 명시됨
- Given: 데이터 변경이 전혀 없는 task의 design 문서
- When: 작성자가 Data Model 섹션 처리 방법을 찾는다
- Then: SKILL.md에 `"N/A — no data changes"` 한 줄 처리 가이드가 명시되어 있다

### AC-5: 출력 예시 일관성
- Given: SKILL.md Step 4 (Post Summary to Jira) 코멘트 예시
- When: Data Model 추가가 코멘트 요약에 영향을 주는지 확인한다
- Then: 영향이 있다면 예시가 갱신되고, 영향이 없다면 변경 없음(현 상태 유지)이 의도적 결정이다

### AC-6: 다른 단계 영향 없음
- Given: plan/impl/test/review 등 다른 단계 스킬
- When: 본 변경 후 다른 스킬 동작을 점검한다
- Then: 다른 스킬은 영향받지 않는다 (surgical change 검증)

## Edge Cases

- **데이터 변경이 일부 모호한 task** (예: 캐시 키 추가): Data Model 섹션의 "도메인 객체" 또는 "데이터 흐름" 하위 항목으로 처리. 가이드에 in-memory 데이터도 대상임을 언급
- **DB 변경은 없으나 API DTO만 추가되는 task**: Data Model의 "API 페이로드" 항목만 채우고 나머지는 생략. fallback 한 줄 처리는 아님
- **Read-only 분석/리포트 task**: "N/A — no data changes" fallback 한 줄 처리
- **마이그레이션이 별도 PR로 분리되는 task**: DB 스키마 항목에서 "마이그레이션 별도: 후속 task #ID 참조" 식 명시 가능
- **상태 전이가 본 task의 핵심인 경우** (예: 워크플로 status 변경): "상태 모델" 항목이 메인이 됨. 다이어그램은 Mermaid stateDiagram 권장
- **순수 문서/설정 변경 task** (예: README, CLAUDE.md 갱신): "N/A — no data changes" fallback. 본 task(MAE-172) 자체가 SKILL.md만 변경하므로 좋은 예시
- **plan 문서가 없는 상태에서 design 호출**: 기존 Step 1 동작 그대로(권장만 제시 후 진행). 본 변경은 영향 없음
