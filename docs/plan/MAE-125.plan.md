# Plan: MAE-125 - [1.2.4] 테스트 시나리오 작성

## Background

상위 Phase 1.2 (MAE-105)는 PreToolUse hook 기반 phase gate를 도입해 워크플로 위반(예: design 없이 impl 진입)을 코드 레벨에서 차단한다. 선행 작업으로 MAE-122(의존 그래프 외부화), MAE-123(`phase-gate.js` 구현)이 이미 완료되었다.

본 작업(MAE-125)은 `hooks/scripts/phase-gate.js`의 동작을 검증하는 자동 테스트 시나리오를 작성한다. 4개 핵심 시나리오를 stdin payload 기반으로 호출하고 exit code/stderr 메시지로 pass/fail을 판정한다. 후속 MAE-126(`hooks.json` PreToolUse 등록) 전에 스크립트 자체의 정확성을 보장하는 단계다.

연관 작업:
- MAE-123 (완료): 검증 대상 스크립트 (`hooks/scripts/phase-gate.js`)
- MAE-124 (진행 중): bypass 메커니즘 — 시나리오 #3은 MAE-124 머지 이후에 실 동작 검증 가능
- MAE-126 (할 일): 본 테스트 통과 후 hook 등록

## Scope

### In Scope
- `hooks/scripts/phase-gate.test.js` 신규 작성 (Node.js 내장 `node:test` 또는 단순 어서션 스크립트, no external deps)
- 4개 핵심 시나리오 자동화:
  1. **차단**: `completedSteps`에 `design` 없이 `jira-task-impl` 호출 → exit 2 + stderr 안내
  2. **통과 (정상 순서)**: 모든 `requires` + `artifacts` 충족 → exit 0
  3. **bypass 통과**: `JIRA_PHASE_GATE_BYPASS=1` 또는 `bypassGate: true` → exit 0 (+ 경고 stderr)
  4. **컨텍스트 없음**: `.jira-context.json` 미존재 → exit 0 (graceful skip, 첫 진입 보호)
- 임시 디렉토리/picture fixture 생성 및 정리 (각 케이스 격리)
- `package.json`의 `scripts.test`에 등록 (또는 `npm test` 진입점 추가/확장)
- 명확한 pass/fail 콘솔 출력

### Out of Scope
- `hooks/hooks.json`에 PreToolUse 등록 (MAE-126)
- bypass 메커니즘 자체의 구현 (MAE-124) — 본 작업은 호출 인터페이스만 검증
- 다른 hook(`session-start.js`, `stop-sync.js`) 테스트
- E2E (실제 Claude Code 세션에서 hook 트리거) — 단위 테스트만
- CI 설정

### 의존성 노트
- 시나리오 #3(bypass)은 MAE-124 머지 이전에 작성은 가능하나 실 동작 검증은 MAE-124 완료 후 가능. 본 plan에서는 **bypass가 구현된 시점의 동작을 가정**한 테스트를 작성하고, MAE-124 미완료 시 해당 케이스는 `skip` 또는 `expected fail`로 표시한다.

## Acceptance Criteria

### AC-1: 테스트 파일 존재 및 단독 실행 가능
- Given: `hooks/scripts/phase-gate.test.js`
- When: `node hooks/scripts/phase-gate.test.js`로 실행
- Then: 외부 의존성 없이 4개 시나리오 모두 실행되고, 종합 결과(통과 N/실패 M)가 stdout에 출력된다. 1개라도 실패하면 exit code 1.

### AC-2: 시나리오 1 — design 없이 impl 호출 차단
- Given: 임시 디렉토리에 `.jira-context.json` `{ "taskId": "TEST-1", "completedSteps": ["init", "start", "plan"] }` 작성
- When: `phase-gate.js`에 stdin으로 `{ "tool_name": "Skill", "tool_input": { "skill": "jira-integration:jira-task-impl", "args": "TEST-1" } }` 전달
- Then: exit code 2, stderr에 한국어 안내 메시지(요구 phase `design` 언급) 포함

### AC-3: 시나리오 2 — 정상 순서 호출 통과
- Given: 임시 디렉토리에 `.jira-context.json` `{ "taskId": "TEST-2", "completedSteps": ["init", "start", "plan", "design"] }` + `docs/design/TEST-2.design.md` 빈 파일 작성
- When: stdin payload `{ "tool_name": "Skill", "tool_input": { "skill": "jira-integration:jira-task-impl", "args": "TEST-2" } }`
- Then: exit code 0, stderr 비어 있음

### AC-4: 시나리오 3 — bypass 플래그 통과 + 경고
- Given: 시나리오 1과 동일한 차단 조건 (design 누락)
- When: `JIRA_PHASE_GATE_BYPASS=1` 환경 변수 설정 후 동일 payload로 호출
- Then: exit code 0, stderr에 bypass 경고 메시지 포함 (예: "Phase gate bypassed")
- 추가 케이스: `.jira-context.json`에 `bypassGate: true` 필드 — 동일하게 통과 + 경고
- 비고: MAE-124 미완료 시 해당 케이스는 `skip`(스킵 사유 출력)으로 표시

### AC-5: 시나리오 4 — context 파일 없음 통과 (첫 진입 보호)
- Given: 임시 디렉토리에 `.jira-context.json`이 존재하지 않음 (그리고 상위 디렉토리에도 발견되지 않도록 격리)
- When: stdin payload `{ "tool_name": "Skill", "tool_input": { "skill": "jira-integration:jira-task-init", "args": "" } }`
- Then: exit code 0, stderr 비어 있거나 정보성 메시지만 (차단 없음)

### AC-6: 격리된 fixture
- 각 시나리오는 독립된 임시 디렉토리(`os.tmpdir()` 하위)에서 실행되어야 하며, 실행 후 정리된다 (다른 시나리오/실제 워크트리의 `.jira-context.json`에 영향받지 않음)
- `phase-gate.js`는 cwd 기반 상향 탐색을 하므로, child process의 `cwd` 옵션을 임시 디렉토리로 지정한다

### AC-7: pass/fail 출력 가독성
- 시나리오별 결과 한 줄씩 출력 (`✓` / `✗` 마커, 시나리오 이름, 실패 사유)
- 마지막에 합계 (`총 N개 중 M 통과, K 실패 (스킵 S)`)

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| MAE-124(bypass)가 본 작업과 병렬로 진행 중이라 `JIRA_PHASE_GATE_BYPASS` env 인식이 아직 미구현일 수 있음 | 중 | 시나리오 3은 MAE-124 미완료 감지 시 자동 skip + 사유 출력. plan/design은 MAE-124의 인터페이스 가정(env 이름, context flag 이름) 기준으로 작성 |
| 임시 디렉토리 격리 실패 시 상위 워크트리의 `.jira-context.json`이 탐색됨 | 높 | (a) `os.tmpdir()`는 기본적으로 워크트리 외부, (b) phase-gate.js의 상향 탐색이 root까지 진행되더라도 `/tmp`까지에는 컨텍스트 없음. 추가로 시나리오 시작 전 `cwd`의 부모 체인에 `.jira-context.json`이 없는지 sanity check |
| `node:test` vs 단순 직접 어서션 — 표준 라이브러리만 사용해야 함 | 저 | Node 18+ 내장 `node:test`/`node:assert` 사용 (의존성 없음). 또는 더 단순한 직접 어서션 + try/catch도 무방. design에서 결정 |
| 상대경로/cwd 처리 실수로 윈도우/macOS 호환성 깨짐 | 저 | `path.join`, `path.resolve` 일관 사용. fileGlob 치환은 phase-gate.js 내부 로직이라 테스트는 결과만 확인 |
| 스크립트 호출 방식 — child_process spawn vs execSync | 저 | `spawnSync('node', [scriptPath], { input, cwd, env, stdio: ['pipe','pipe','pipe'] })` 권장. status/stderr 직접 검사 가능 |
| 미래에 `phase-gate.config.json`이 변경되면 정상 케이스(시나리오 2)가 깨짐 | 중 | 시나리오 2 fixture는 현재 config의 `phases.impl.requires`/`artifacts`를 기준으로 구성. config 변경 시 본 테스트도 함께 업데이트 (test의 책임) |

## Edge Cases

- **Node 버전 차이**: `node:test`는 Node 18+ 안정. 프로젝트 최소 Node 버전 확인 후 design에서 채택 여부 결정 (필요 시 plain assertion으로 대체)
- **`spawnSync`의 stdin EOF**: payload 문자열을 `input`으로 전달하면 자동 close. 빈 입력 시나리오는 `input: ''`
- **stderr가 한국어**: 인코딩 비교는 byte 비교가 아니라 문자열 includes로
- **MAE-124 미완료 감지 방법**: `phase-gate.js` 코드 grep으로 `JIRA_PHASE_GATE_BYPASS` 문자열 존재 여부 확인 → 없으면 skip
- **상위 디렉토리에 우연히 `.jira-context.json`이 있는 환경**: 시나리오 4는 임시 디렉토리에서 child의 부모 체인을 root까지 점검하고 `.jira-context.json`이 어디에도 없을 때만 실행 (있으면 skip + 사유)
- **CI 미적용**: 본 작업은 `npm test` 진입점만 보장. CI 등록은 후속 작업
