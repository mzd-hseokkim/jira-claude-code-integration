## Background

`jira-task-discover` 스킬(MAE-115)이 작성되어 `Skill` 도구로 직접 호출은 가능하지만, 사용자 진입점인 `/jira-task <action>` 슬래시 커맨드에는 아직 `discover` 액션이 등록되어 있지 않다. 그 결과 다음과 같은 문제가 있다:

1. 사용자가 `/jira-task discover "주제"`를 입력해도 라우팅이 없어 동작하지 않거나 도움말로 폴백된다.
2. argument-hint, action 목록(`description`, 라우팅 섹션) 등 메타 정보가 신규 액션을 반영하지 않는다.
3. discover 스킬은 `--lite`, `--from <파일경로>` 같은 부가 인자를 받는데, 이를 사용자 입력 그대로 스킬에 전달하는 위임 패턴이 라우팅 레이어에 명시되어야 한다.

본 태스크는 `commands/jira-task.md`에 `discover` 액션 분기를 추가하여, 기존 `create`/`init`이 사용하는 "원문 인자 그대로 위임" 패턴과 동일하게 discover 진입점을 마련한다. 이로써 MAE-118(완료된 단계 인식 측)과 함께 `/jira-task discover` UX가 끝부터 끝까지 작동하게 된다.

## Scope

### In Scope

- `commands/jira-task.md` 단일 파일 편집:
  - YAML frontmatter `description`의 actions 목록에 `discover` 추가
  - `argument-hint`에 `discover` 추가
  - "Argument Parsing" 섹션의 action 목록에 `discover` 추가
  - "Action Routing" 섹션에 `### discover [자연어 주제] [--lite] [--from <파일경로>]` 분기 추가 (Skill 도구로 `jira-integration:jira-task-discover` 호출)
  - 인자 위임 예시 명시 (`create`/`init`과 동일한 "원문 그대로 전달" 규약)
- TASK-ID Auto-Detection 섹션의 "Not required for ..." 목록에 `discover` 포함 여부 결정 (discover는 TASK-ID를 받지 않으므로 포함)
- 분기 위치는 워크플로 순서 기준으로 `create` 다음, `init` 앞 또는 사이의 자연스러운 곳에 둔다 (discover → create → init 순)

### Out of Scope

- discover 스킬 코드 변경 (MAE-115 완료 범위)
- `templates/requirements.template.md` 변경 (MAE-117 완료 범위)
- `.jira-context.json`의 `completedSteps` 유효 단계 확장 (MAE-118의 책임)
- `jira-task-create`의 `--from-requirements` 통합 (MAE-116의 책임)
- CLAUDE.md, README의 워크플로 다이어그램 갱신 (MAE-120, MAE-121)
- `discover` 액션을 `auto`(`/jira-task auto`)에 자동 포함시키는 변경 — auto 흐름은 별도 검토 필요. 본 태스크에서는 명시적 호출만 지원
- `commands/jira.md`(도움말) 변경 — 본 태스크는 `commands/jira-task.md`만 다룸. 도움말 갱신이 필요하면 MAE-120 문서 갱신과 함께 처리

## Acceptance Criteria

### AC-1: 액션 메타 정보 갱신

- **Given**: `commands/jira-task.md`의 YAML frontmatter
- **When**: 본 태스크 구현 완료 후 파일을 읽는다
- **Then**:
  - `description` 필드의 actions 나열에 `discover`가 포함된다
  - `argument-hint`에 `discover`가 다른 액션과 동일한 형식으로 포함된다

### AC-2: Argument Parsing 섹션 갱신

- **Given**: 문서의 "Argument Parsing" 섹션
- **When**: action 종류 정의를 확인한다
- **Then**:
  - `discover`가 `One of …` 목록에 추가된다
  - "Not required for …" 목록(`create`, `init`, `report`, `status`)에 `discover`가 추가된다 (discover는 TASK-ID 대신 자연어 주제를 받음)

### AC-3: Action Routing 분기 존재

- **Given**: 문서의 "Action Routing" 섹션
- **When**: `discover` 라우팅을 검색한다
- **Then**:
  - `### discover [자연어 주제] [--lite] [--from <파일경로>]` (또는 동등한 인자 시그니처) 헤딩이 존재한다
  - 본문에 `Skill({ skill: "jira-integration:jira-task-discover", args: "<사용자가 입력한 discover 이후의 전체 인자를 그대로 전달>" })` 호출 패턴이 명시된다
  - 인자 예시 최소 3건이 제공된다 (예: `discover "사용자 알림"`, `discover "..." --lite`, `discover --from docs/req.md`)

### AC-4: 위임 패턴 일관성

- **Given**: 기존 `create`/`init` 라우팅이 사용하는 "원문 인자 그대로 전달" 강제 규칙
- **When**: discover 분기를 동일 패턴으로 비교한다
- **Then**: 표현·형식이 `create`/`init` 분기와 일관되며, "Claude가 직접 처리 금지, Skill 도구만 사용" 강제 규칙은 (선택적으로) 명시되거나 다른 분기와 동일한 강도로 표현된다

### AC-5: 회귀 없음

- **Given**: 기존 액션(`start`, `plan`, `design`, `impl`, `test`, `review`, `pr`, `merge`, `done`, `report`, `status`, `auto`, `clean`, `create`, `init`)의 라우팅
- **When**: 변경 후 파일을 검토한다
- **Then**: 기존 라우팅의 헤딩·Skill 호출문이 의도치 않게 변경되지 않는다 (스코프 밖 줄은 surgical 원칙대로 보존)

### AC-6: 빌드/문법 무결성

- **Given**: `commands/jira-task.md`은 슬래시 커맨드 정의 마크다운
- **When**: 변경 후 파일을 파싱한다
- **Then**:
  - YAML frontmatter가 유효하다 (frontmatter 닫힘, 들여쓰기 정합)
  - 마크다운 헤딩 구조가 깨지지 않는다
  - 코드 블록의 백틱 짝이 맞는다

## Edge Cases

- **`discover` 인자가 비어 있는 경우**: 라우팅은 빈 문자열을 그대로 전달 → discover 스킬 Step 0이 사용자에게 주제를 다시 물음. 라우팅 레이어에서 별도 분기 불필요.
- **`discover --lite`만 입력**: 자연어 주제 없이 플래그만. 동일하게 빈 주제로 위임 → 스킬이 처리.
- **`discover --from path/with space.md`**: 공백 포함 경로. CLI 인자 quoting은 사용자 책임. 라우팅은 원문 전달 정책이라 별도 처리 없음.
- **TASK-ID 자동탐지 충돌**: 사용자가 `feature/MAE-XXX` 브랜치에서 `/jira-task discover ...`를 호출해도 discover는 TASK-ID를 받지 않는 액션이므로 자동탐지 결과를 무시한다. 이를 "Not required for" 목록에 명시함으로써 처리.
- **대소문자/오타**: `Discover`, `DISCOVER`, `discov` 등의 변형은 라우팅에서 매칭 실패. 이는 기존 액션도 동일한 정책 — 본 태스크는 정책 변경하지 않음.
- **다른 액션과의 토큰 충돌**: `discover`는 기존 어떤 액션과도 prefix 충돌이 없다 (`done`, `design`, `de…` 모두 다름).

## Implementation Strategy

본 태스크는 **단일 마크다운 문서의 surgical 편집**으로 코드 로직 변경이 없다. 따라서 design 단계는 **경량(lightweight)** 으로 진행해도 충분하다 (분기 텍스트 초안 정도면 됨).

권장 흐름: `plan ✓ → (경량) design → impl → test → review → merge → done`

- **design 경량화**: 분기 본문 초안 + 인자 예시 3건 + 기존 분기와의 표현 정렬 표만 담는다.
- **impl**: 1~3회의 `Edit` 도구 호출로 frontmatter, Argument Parsing, Action Routing 세 위치를 수정. 마지막에 `.claude-plugin/plugin.json`의 `version`을 patch 또는 minor로 증가.
- **test**: 자동 테스트는 불필요. 수동 검증 — `commands/jira-task.md`을 다시 읽어 모든 AC가 충족되는지 확인. 가능한 경우 실 슬래시 커맨드 호출(`/jira-task discover "테스트 주제" --lite`)로 라우팅이 discover 스킬에 도달하는지 확인.
- **review**: 변경 줄이 3~10줄 내외로 surgical 원칙 충족 여부 검토.
