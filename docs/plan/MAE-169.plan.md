## Background

### 현재 상황

`skills/jira-task-discover/SKILL.md`의 Step 4 "Generate Requirements Document"는 LLM이 다음 4종 항목을 합성한다.

1. **Functional Requirements** (FR)
2. **Edge Cases**
3. **Out of Scope**
4. **Open Questions**

이 항목들은 (a) Step 2(코드베이스 탐색) 결과, (b) Step 3(사용자 답변), 그리고 (c) LLM의 자체 합성으로부터 만들어진다. 그러나 **현재 산출 항목에는 어디서 유래했는지를 표시하는 메타 정보가 없다**.

### 문제

추적 정보가 없기 때문에 다음과 같은 사후 검증이 불가능하다.

- LLM이 코드베이스에 존재하지도 않는 기능을 FR에 적어 넣어도, 사후에 누가 만든 것인지 식별할 수 없다 (할루시네이션 검증 불가)
- 사용자 답변과 무관한 항목이 추가되어도, 그것이 LLM 창의적 합성인지 답변에서 유래했는지 알 수 없다
- 후속 단계(Confirm Gate, Conflict Detection, plan/design)에서 항목별 신뢰도 차등 처리 불가
- 동일 주제로 재실행 시, 이전 결과의 어느 부분을 보강해야 하는지 판단 곤란

### 영향도

discover 스킬은 후속 `jira-task-create`가 그대로 Jira 이슈로 변환하는 입력이다. 즉, discover 산출물의 신뢰성이 낮으면 잘못된 이슈가 자동 생성되는 위험으로 직결된다. **trace marker는 이 신뢰성을 사후 검증 가능하게 만드는 인프라 변경**이며, MAE-168(Confirm Gate)·MAE-170(Conflict Detection)·MAE-171(Template 강화)과 함께 1.1 phase 품질 강화 묶음의 핵심 축이다.

## Edge Cases

- **Step 3에서 모든 답변이 "Other → (빈)"인 경우**: 답변이 `TBD`로 기록되고, 답변에서 유래한 marker는 `*(source: Q<N>)*`로 표기되되 본문에 "TBD"가 들어간다. 합성 항목은 `*(synthesized)*` 또는 `*(code: ...)*`만 남게 됨. SKILL.md 가이드에 이 케이스 한 줄 노트.
- **`--from` 모드로 import한 항목**: import 베이스 본문 항목에는 별도로 `*(source: from)*` 또는 import 경로 표기 같은 변형이 필요할 수 있으나, 본 이슈는 description에 그 케이스가 명시되어 있지 않음. **default/`--lite` 두 모드 우선 처리**, `--from` 모드 marker 변형은 후속 결정으로 두고 본 이슈에서는 동작은 하되 별도 형식 강제 안 함 (또는 `*(source: from)*` 1개 추가 명시 — design 단계에서 결정).
- **Step 2 결과가 0건 (관련 영역 미발견)**: codebase context가 없으므로 `code:` marker가 부여될 수 없다. 모든 합성 항목이 `*(source: Q<N>)*` 또는 `*(synthesized)*`로 한정됨. 이 케이스는 자연스러우므로 별도 처리 불필요.
- **하나의 항목이 여러 답변에서 유래한 경우**: 멀티 마커 (`*(source: Q1+Q3)*`) 또는 가장 강한 1개만 표기 — description에 명시 안 됨. **단일 표기 원칙**으로 가되, 명백히 둘 이상이면 콤마 구분 (`*(source: Q1, Q3)*`)으로 design 단계에서 확정.
- **하나의 항목이 여러 코드 위치에서 유래**: 동일 원리로 `code:` 측에 multi-path 가능 (`*(code: src/a.ts:10-20, src/b.ts:5-15)*`) — design 단계에서 형식 미세 확정.
- **Open Questions 섹션 항목**: Open Questions는 본질적으로 "결정 보류된 항목" — 답변이 부족해서 생긴 것이므로 `*(source: Q<N>)*`(어느 질문 답변이 부족했는지)가 자연스러움. SKILL.md 가이드에 명시.
- **Edge Cases 섹션 항목 자체에 marker 필요?**: Edge Cases는 거의 항상 LLM 합성이라 `*(synthesized)*` 또는 `*(code: ...)*` (코드 분석에서 도출된 경우) 표기. 답변 직접 매핑은 드물지만 가능 (예: 사용자가 "동시 호출 시 어떻게?"라 답하면 `*(source: Q3)*`).
- **`docs/requirements/<slug>.requirements.md` 재실행 (slug 충돌로 `-2` 부여)**: marker는 매 실행마다 새로 부여됨. 이전 파일과의 marker 일관성은 보장 안 됨 (각 산출물 단위 추적이라 정상).

- **다른 파일 변경 가능성**: 사실상 SKILL.md + plugin.json 2개로 한정.
- **테스트 방식**: discover 스킬을 dummy topic으로 호출해 산출물의 marker 일관성을 sanity check (test 단계).

### 형식 표준 (확정안)

본 plan 단계에서 형식의 골격을 다음과 같이 잠정 확정한다 (design 단계에서 detail 미세 조정).

```
| 케이스 | Marker 형식 | 사용 시점 |
|--------|-------------|----------|
| 답변에서 유래 | *(source: Q<N>)*       | Q<N> 답변에서 직접 도출 |
| 코드에서 유래 | *(code: <path>:<line-range>)* | Step 2 발췌에서 직접 도출 |
| 둘 다       | *(source: Q<N>, code: <path>:<line>)* | 둘 다에서 도출 |
| 둘 다 없음   | *(synthesized)*       | LLM 창의적 합성 (답변·코드 어느 쪽에도 근거 없음) |
```

### Marker 부여 대상 4종 vs 비대상

| 대상 (marker 부여) | 비대상 (답변 직접 매핑이라 marker 불요) |
|----|----|
| Functional Requirements | Stakeholders |
| Edge Cases | Goals & Success Criteria |
| Out of Scope | Constraints |
| Open Questions | Non-functional Requirements |

비대상 4종은 답변을 그대로 옮긴 섹션으로, 출처가 자명(=Step 3 답변)하므로 marker 불요. 대상 4종은 답변+코드+LLM 합성이므로 추적이 필요.
