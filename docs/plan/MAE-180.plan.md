## Acceptance Criteria

### AC-1: review 1회 = 양쪽 파일 각 1건 기록
- Given: 정상 review가 수행되어 Step 4가 완료됨
- When: Step 5 진입 직전 append 단계가 실행됨
- Then: `docs/review-log/<TASK-ID>.review.json`에 entry 1개, `docs/review-log/_index.jsonl`에 새 줄 1개가 추가된다

### AC-2: 같은 task 재리뷰 누적
- Given: `docs/review-log/<TASK-ID>.review.json`에 이미 entry 1개가 있음
- When: 같은 task에 대해 review가 재실행되어 append 단계가 실행됨
- Then: per-task JSON `entries[]`에 push되어 길이 2가 되고, `_index.jsonl`에는 새 줄이 1줄 더 추가된다(파일이 truncate되지 않음)

### AC-3: Request Changes도 append
- Given: subagent 결과가 Request Changes
- When: Step 4가 완료됨
- Then: `completedSteps`에 `"review"`가 추가되지 않더라도 양쪽 로그 파일에는 1건씩 기록된다

### AC-4: append 실패 시 비차단
- Given: append 단계에서 디스크 권한 오류 또는 JSON 직렬화 오류 발생
- When: 예외가 발생함
- Then: stdout에 `⚠️ review-log append failed: <reason>` 한 줄이 출력되고, Step 5(Post Review to Jira)가 정상 진행된다 (전체 워크플로 종료 코드는 성공)

### AC-5: 스키마 필수 필드 100%
- Given: append가 성공
- When: 저장된 JSON entry를 검사
- Then: `taskId`, `timestamp`(ISO8601 UTC), `reviewerVersion`(12자 hex), `outcome`(Approve/Request Changes/Needs Discussion), `findings`(array), `severityCounts`({critical, warning, info}), `falsePositive`(null), `userOverride`(null) 필드가 모두 존재한다

### AC-6: 민감정보 redact 적용
- Given: subagent의 finding `message`에 `sk-...`/`Bearer ...`/`xoxb-...` 등 Story 1 정의 패턴이 포함됨
- When: append 단계가 실행됨
- Then: 저장된 entry의 해당 message 필드는 `***REDACTED***` 형태로 치환되어 있다

### AC-7: append 오버헤드 < 200ms
- Given: 정상적인 로컬 파일 시스템(SSD)
- When: append 단계가 실행됨
- Then: append 단계 시작~종료 사이의 wall-clock 시간이 200ms 미만이다 (수동 측정 1회/PR로 검증 가능)

| # | 결정 | 대안 | 선택 이유 | 영향 |

| 1 | append를 SKILL.md의 별도 단계(Step 4.7)로 끼워넣고, main 세션이 직접 Bash로 수행 | (a) subagent 내부에서 직접 append, (b) Step 5 코멘트 게시 직후 append | (a)는 subagent 출력 단일 진실 원칙 위반. (b)는 Jira 게시 실패 시 로그 누락. main 세션이 Step 4 결과를 받아 직접 쓰는 게 워크플로상 가장 자연스럽고 비차단 처리 쉬움 | scope: append 책임이 main 세션에 집중. risk: SKILL.md 변경 범위 명확 |
| 2 | `reviewerVersion`은 SKILL.md sha256 prefix 12자만 사용 (agents 파일 미포함) | agents/jira-reviewer.md까지 포함하여 합산 해시 | 본 단계에서는 단순화 우선. Phase 3 자동 calibration에서 agents 변경 추적 필요해지면 확장 | scope: 단순. risk: reviewer 동작 변경이 agents 파일에서만 일어나면 동일 버전으로 기록됨 — 알려진 trade-off |

| 4 | append 실패 시 재시도 없음 — 1회 시도 후 경고만 | 지수 backoff 재시도, 별도 retry 큐 | best-effort 정책상 단순화. 재시도 비용 > review 흐름 차단 비용은 아님 | scope: 단순. risk: 일시적 디스크 락 시 단발 손실 가능 — 허용 |

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| `_index.jsonl` 동시 append 시 줄 섞임 (Windows / NFS) | Medium — 분석 시 깨진 줄 발생 | OS 단의 append 원자성에 의존(POSIX `O_APPEND`). 줄 단위 짧음. Windows에서는 PR 단계에서 1회 수동 검증. 큰 문제면 file lock 도입 — 본 plan은 이월 |
| Story 1의 redact 유틸이 Bash로 직접 호출 가능한 형태가 아닐 가능성 | High — AC-6 미달 | Task 5 시작 직전 Story 1 산출물 형태 확인. Bash에서 호출 어려우면 inline regex sed로 동등 패턴 적용 (Open Item) |
| `reviewerVersion` 해시 산출이 worktree마다 다른 SKILL.md 경로를 참조 | Medium — 잘못된 hash | SKILL.md 절대경로를 plugin 캐시 경로로 고정하지 말고, 실행 중인 스킬 본체(스킬 base directory의 SKILL.md)를 참조 |
| append가 Step 4.7로 추가되며 SKILL.md 단계 번호 정합성 깨짐 | Low — 문서/로그 라인 참조 깨짐 | Step 4.7로 명명(소수점)해 기존 5/6 번호 보존. 하위 스킬에서 Step 5/6 참조하는 부분이 있는지 grep 검증 |
