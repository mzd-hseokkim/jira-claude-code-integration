# Approach: MAE-387 - Phase 2 — cycle/lead time + 사람별 처리량 + aging WIP

- **Level**: L2 (Story)
- **Source**: N/A — discover 생략 (Subtask 직접 진행). 입력은 Jira description 완료 기준.

## Approach Summary (L2 Story)

Phase 1(MAE-386)이 깐 `metrics-store`(SQLite + JSON 미러) · `GET /metrics` · AnalyticsView 위에 시간·사람 관점 지표 4종을 추가한다: lead time(`resolutiondate - created`), cycle time 근사(`issue_snapshot`에서 statusCategory가 `indeterminate`로 처음 잡힌 날 → `resolutiondate`), 사람별 주간 완료·현재 WIP, aging WIP(In Progress 경과일). 새 store 메서드를 `/metrics` 응답에 합치고 클라이언트에 경량 SVG 차트 + 테이블을 추가한다. 스키마 변경 없음 — 기존 `issue_current`/`issue_snapshot` 컬럼으로 전부 계산 가능.

## Architecture

핵심 seam은 **`/metrics` 응답 계약**이다. 서버는 store 메서드 호출 → JSON 필드 추가, 클라이언트는 `useMetrics`가 그 필드를 매핑한다. 기존 4필드(`spaceId/weeks/statusDistribution/wip/throughput`)에 `leadTime`, `cycleTime`, `perAssignee`, `agingWip`를 **추가만** 한다(기존 필드 유지 → 하위 호환).

store는 SQLite + JSON 두 구현을 항상 동시에 맞춰야 한다(둘 다 동일 시그니처). cycle time은 `issue_snapshot`의 일 단위 근사라 정확도 한계가 있음을 응답/UI에 "근사"로 표기.

```
issue_current / issue_snapshot
   └─ store.getLeadTime / getCycleTime / getPerAssignee / getAgingWip   (sqlite + json 미러)
        └─ routes/metrics.js  →  res.json({ ...기존, leadTime, cycleTime, perAssignee, agingWip })
             └─ useMetrics() 매핑 → AnalyticsView → 차트/테이블 컴포넌트
```

## Key Decisions

| # | 결정 | 대안 | 선택 이유 |
|---|---|---|---|
| 1 | 스키마 변경 없이 기존 컬럼만 사용 | snapshot에 firstInProgressAt 컬럼 추가 | 완료 기준이 근사 cycle time 허용 → 마이그레이션 비가역 비용 회피 (데이터 모델 차원: ruling out) |
| 2 | `/metrics` 응답에 필드 **추가만**, 기존 4필드 유지 | 응답 구조 재편/버저닝 | 클라이언트 하위 호환 + Phase 1 테스트 무변경 (인터페이스 계약 차원) |
| 3 | cycle time = snapshot 최초 `indeterminate` 날짜 → resolutiondate, 일 단위 | 정확한 status 전이 changelog 추적 | snapshot이 일 1회 → 일 단위가 데이터 한계. UI에 "근사" 명시 |
| 4 | 무할당을 perAssignee에서 별도 버킷 처리 | null assignee 제외 | description 완료 기준 명시. 누락 방지 |
| 5 | 집계는 store 메서드로, route는 조합만 | route에서 직접 쿼리 | Phase 1 패턴 유지 + sqlite/json 미러 일관성 (기존 패턴 답습) |
