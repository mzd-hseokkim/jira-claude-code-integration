# Approach: MAE-386 - Phase 1 — 스페이스 디스커버리 + JQL collector + SQLite + status/throughput

- **Level**: L2 (Story)
- **Source**: N/A — discover 생략 (issue description 기반). issuetype은 Subtask이나 SQLite 스키마 신설 + 신규 REST 계약으로 L2 격상.

## Approach Summary (L2 Story)

Analytics 뷰의 데이터 파이프라인을 구축한다. `workspaces.json` 레지스트리에서 (siteBaseUrl, projectKey)를 도출하는 스페이스 디스커버리, project별 JQL을 5분 주기로 수집하는 신규 collector(`jira-metrics.js`), 결과를 SQLite(`metrics.db`, 실패 시 JSON 폴백)에 영속화하는 store를 만든다. 서버는 `GET /spaces`(선택기 목록)·`GET /metrics?space=&weeks=`(집계 JSON) 두 엔드포인트를 추가하고, 클라이언트 헤더 view-toggle에 분석 모드 + 스페이스 선택기, status 분포/WIP·주별 throughput SVG 차트(empty/loading/error state)를 붙인다. 기존 worktree 모니터 경로(store/jira collector)는 건드리지 않고 별도 모듈로 추가한다.

## Architecture

핵심 seam은 **수집 → 영속화 → 집계 조회**의 경계다. 못 바꾸는 결정은 두 가지: (1) SQLite 스키마(`spaces`/`issue_current`/`issue_snapshot`)와 (2) REST 응답 계약.

- 디스커버리(`metrics-spaces.js`): `workspaces.loadAndPrune()` → 각 root의 credentials/`JIRA_DEFAULT_PROJECT`/key 접두사 추론 → (site, projectKey) dedupe.
- collector(`collectors/jira-metrics.js`): 스페이스별 JQL 페이지네이션 fetch → metrics store에 upsert. 기존 `collectors/jira.js`(worktree 단건 refresh)와 분리 — 책임/생명주기 다름.
- metrics store(`metrics-store.js`): better-sqlite3 래퍼. 모듈 로드 시 한 번 capability probe → 실패 시 JSON 폴백 구현으로 스왑(`store.js`의 factory swap-point 패턴과 동일 사상).
- 조회: `GET /metrics`는 store의 집계 쿼리(주별 throughput, 현 status 분포)를 JSON으로 반환. 서버는 raw row를 클라이언트로 흘리지 않는다.

```
workspaces.json → metrics-spaces(discover) → spaces 테이블
                                            ↘ jira-metrics collector (5분 tick)
                                                 → issue_current (upsert) + issue_snapshot (일 단위 append)
GET /spaces   ← spaces 테이블
GET /metrics  ← issue_current(분포) + issue_snapshot(throughput)
```

## Key Decisions

| # | 결정 | 대안 | 선택 이유 |
|---|---|---|---|
| 1 | SQLite 3-테이블: `spaces`, `issue_current`(이슈당 1행 upsert), `issue_snapshot`(이슈×일 1행 append) | 단일 events 테이블 | issue_current로 현 status 분포 O(1), snapshot으로 주별 throughput. 완료기준(분포+throughput) 직접 매핑 |
| 2 | throughput 정의 = `issue_snapshot`에서 resolutiondate가 해당 주에 속하는 이슈 수 | updated 기반 추정 | 완료기준 "완료/주"는 해결 시점 기준이어야 정확 |
| 3 | better-sqlite3 미설치/네이티브 빌드 실패 시 JSON 파일 폴백 (모듈 로드 시 1회 probe) | sqlite 강제 의존 | description 명시 폴백 요구. 플러그인 배포 환경 네이티브 모듈 불확실성 회피 |
| 4 | metrics collector를 기존 `collectors/jira.js`와 별도 모듈로 신설 | 기존 collector 확장 | 기존은 worktree 단건 stale-refresh, 신규는 project 단위 bulk JQL — 생명주기/책임 분리 (Surgical) |
| 5 | `GET /metrics`는 서버에서 집계 후 JSON 반환 (raw row 미노출) | 클라이언트 집계 | 계약 안정성, 클라이언트 경량화. 외부 노출 인터페이스 경계 고정 |
| 6 | projectKey 도출: `JIRA_DEFAULT_PROJECT` 우선 → 없으면 이슈 key 접두사 추론 | site만 사용 | description 명시. JQL `project=KEY` 필수 |
| 7 | snapshot 멱등성: (issueKey, snapshotDate) PK로 같은 날 재수집 시 upsert | append-only | 5분 tick이 하루 다회 실행 → 일 단위 1행 유지 (순서/멱등) |

설계 차원 ruling: 데이터 모델/스키마(#1,#7) · 인터페이스/API 계약(#5,#2) · 멱등성·순서(#7) 결정. 보안·권한은 기존 credentials 체인 재사용으로 신규 결정 없음. 동시성: 단일 collector tick·순차 fetch라 신규 동시성 결정 없음.

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| better-sqlite3 네이티브 빌드 실패(플랫폼별) | 영속화 불가 | optionalDependency + 로드 probe → JSON 폴백, 폴백 경로도 테스트(T4) |
| 대규모 project JQL(`updated>=-90d`) 페이지네이션 부하/rate limit | tick 지연·429 | 페이지 단위 backoff, 기존 collector의 429 abort 패턴 차용 |
| `JIRA_DEFAULT_PROJECT` 미설정 + 이슈 key 접두사 추론 실패 | 스페이스 누락 | 도출 실패 스페이스는 creds/projectKey '미해석'으로 표기, 선택기에서 비활성 |
