# 작업 등급 (L1 / L2 / L3) — 판정·확정·기록

기준: 표준 `00-ai-native-sdlc-process` 3장 "등급 정하기", SD-COM-GAT-001·002. start(태스크 1건)와 loop 준비 패스(큐 일괄)가 이 파일을 따른다. 이후 단계는 context `level`만 읽는다 — issuetype으로 등급을 추정하지 않는다.

## 이미 정해진 등급

이슈 labels에 `sdlc-L1|L2|L3`가 있으면 그 등급을 쓰고 다시 묻지 않는다. 위험 신호는 그 등급을 확정한 Jira 코멘트(`## SDLC Level`)에서 읽는다. context `level`이 없으면 기록만 맞춘다(아래 "context").

Epic은 등급을 붙이지 않는다. 등급은 PR이 나오는 작업 단위(Story·작업·Subtask)에만 붙인다.

## 판정 (에이전트 제안)

이슈 요약·설명·AC·연결 문서를 읽고 순서대로 답한다. 애매하면 높은 등급으로 정한다.

1. 제품 동작을 새로 정하거나 바꾸는가(새 기능, 요구사항 변경)? → L3
2. 위험 신호가 하나라도 있는가? → L2
3. 바뀌는 내용을 한 문장으로 설명할 수 있는가? → L1, 아니면 L2

위험 신호: ① DB 스키마·데이터 모델 ② 외부 API 계약 ③ 트랜잭션 경계·동시성·멱등성 ④ 인증·권한·개인정보 ⑤ ADR이 필요한 결정. 등급과 별개로 해당 번호를 모두 적는다(L3여도 위험 신호가 있으면 plan을 기술 책임자가 승인한다).

## 확정 (작업 담당자)

제안은 등급, 위험 신호 번호와 이름, 근거 한두 줄로 보여 주고 확정을 받는다. `AskUserQuestion`이 있으면 선택지(제안 등급을 첫째 + "(제안)", 나머지 두 등급)로, 없으면 텍스트로 묻고 답을 기다린다. 사용자가 고르지 않으면 진행하지 않는다 — 추정으로 확정하지 않는다.

## 기록

1. **라벨**: 기존 labels에서 `sdlc-L*`를 빼고 확정 등급 라벨을 더해 통째로 쓴다(`update`는 labels 전체 교체).
   ```bash
   python3 "<scripts>/jira-cli.py" update <KEY> '{"labels":[<기존 라벨...>,"sdlc-L2"]}'
   ```
2. **코멘트**:
   ```markdown
   ## SDLC Level
   - 등급: L2
   - 위험 신호: ① DB 스키마·데이터 모델   (없으면 "없음")
   - 근거: <한두 줄>
   - 확정: <whoami displayName> (에이전트 제안: L2)
   ```
3. **context**: `jira-context-update.py`의 `--patch '{"level":"L2","riskSignals":[1]}'` — worktree-local과 aggregate 둘 다에 반영된다. 위험 신호가 없으면 `[]`. 라벨이 바뀌었으므로 같은 호출에 `--cache-issue <get 출력 파일>`을 붙여 `cachedIssue`도 새로 받는다(start는 Step 6에서 한 번에 한다).

## 등급을 바꿀 때

작업 중 위험 신호를 새로 발견했거나 한 문장으로 설명할 수 없게 되면 멈추고 사용자에게 알린다. 다시 확정을 받아 위 세 가지를 모두 갱신한다(L1 → L2면 approach부터 진행).
