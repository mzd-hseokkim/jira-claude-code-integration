# Breakdown Level Decision (Step 5 보조 자료)

분해 형식을 입력 규모에 맞게 LLM이 판단한다. **항상 트리를 강제하지 않는다** — 작은 작업은 Single이 정답.

## 3 레벨 정의

| 레벨 | 형태 | 적용 조건 (감각 기준) |
|---|---|---|
| **L1 Single** | 작업 1건 (Epic/Story 생략) | 단일 PR 범위 / 단일 버그 수정 / 변경 파일 ≲ 5개 / FR 1-2건 |
| **L2 Story+Subtasks** | Story 1 + Sub-task N | 한 영역 내 다단계 작업 / FR 3-6건 / 한 사람이 1주 안에 끝낼 수 있는 규모 / 별도 Epic이 과한 경우 |
| **L3 Epic+Stories+Subtasks** | Epic + Story N + Sub-task M | 여러 영역 병렬 작업 / FR 7+ / Goals 다수 / "도입/구축/리뉴얼" 어감 / 다중 PR 예상 |

## 추천 신호표

`Step 4.5 synthesis-confirm` 직전 LLM이 합성 산출물을 입력으로 1개 레벨을 추천한다. 신호 우세에 따른 점수 합산이 아니라 **지배 신호 1-2개로 결정**. 모호하면 L2 default.

| 신호 | L1 | L2 | L3 |
|---|---|---|---|
| FR 개수 | 1-2 | 3-6 | 7+ |
| Goals 개수 | 1 | 1-2 | 3+ |
| Codebase Context 면적 | 파일 1-3개 | 파일 4-10개 | 영역 다수 |
| 변경 영역 다양성 | 단일 모듈 | 한 영역 내 | 여러 영역 |
| Topic 어감 | "fix", "단일", "버그" | "확장", "추가" | "도입", "구축", "리뉴얼" |
| 의존/병렬성 | 단일 PR | 순차 | 병렬 PR 가능 |

**FR 개수는 레벨만 정한다. 서브태스크 개수를 정하지 않는다.** FR은 문서 단위이고 서브태스크는 머지 단위다. FR 여러 건이 같은 파일을 고치는 일이면 서브태스크는 하나다. FR을 1:1로 서브태스크에 흘려보내는 것이 과분해의 가장 흔한 경로다.

## 서브태스크 도출 순서 (파일군 우선)

레벨을 정한 다음, **서브태스크를 바로 쓰지 않는다.** 아래 순서를 거친다. FR 목록에서 서브태스크로 곧장 내려가는 것이 과분해의 실질적 원인이다.

1. **파일군(touch set) 나열** — `Step 2 Codebase Context`의 발췌 파일 + FR을 입력으로, "이 일을 끝내려면 어떤 파일/모듈을 고쳐야 하는가"를 먼저 나열한다. 아직 서브태스크가 아니라 파일 목록이다.
2. **파일군 묶기** — 같이 고쳐야 말이 되는 파일들을 한 덩어리로 묶는다. 한 덩어리 = 한 번의 수정 = 한 번의 머지.
3. **덩어리 1개 = 서브태스크 1개** — 덩어리 수가 곧 서브태스크 수다. FR 개수와 일치할 이유가 없다.
4. **경계 규칙으로 검산** — 아래 세 조건으로 각 서브태스크를 다시 본다.

파일군을 그릴 수 없으면(Codebase Context 0건 등) 서브태스크를 만들지 않는다. 근거 없이 나눈 트리보다 스토리 1건이 낫다.

각 서브태스크는 확정된 파일군을 `범위:` 줄로 **반드시** 기록한다. 이 줄이 없으면 이후 단계(`synthesis-confirm` 과분해 경고, `create` Step 4.9)가 겹침을 판정할 근거를 잃는다.

## 서브태스크 경계 규칙

서브태스크를 **어디서 끊을지**는 아래 규칙으로 정한다.

**서브태스크 하나 = worktree 하나 = 머지 하나다** (`jira-task-init`이 태스크마다 worktree를 만든다). 따라서 **한 서브태스크가 한 파일군을 독점해야 한다.** 같은 파일을 건드리는 항목을 나누면 병렬로 굴릴 수 없고, 순차로 굴려도 리베이스만 붙는다.

유효한 경계는 대개 한 줄이다:

| 경계 | 예 |
|---|---|
| 서버 / 화면 | `[서버] 실패 사유를 분류 코드로 저장` / `[화면] 저장된 사유를 읽어 표시` |
| 계약 / 구현 | `공용 스키마 정의` / `각 경로에서 스키마 채우기` |
| 기능 / 마이그레이션 | `신규 필드 추가` / `기존 레코드 소급 변환` |

**개수로 판정하지 않는다.** 정말 15건이 필요한 일도 있고 2건이면 끝나는 일도 있다. 대신 서브태스크마다 아래 셋을 통과하는지 본다.

1. **파일 독점** — 다른 서브태스크와 같은 파일/모듈을 고치는가? 그렇다면 합친다. 셋 중 유일하게 기계적으로 판정되는 조건이다.
2. **독립 머지** — 이것만 머지했을 때 저장소가 말이 되는 상태로 남는가? "default를 붙인다", "회귀 테스트를 추가한다" 같은 항목은 대개 앞 항목의 일부지 별건이 아니다.
3. **독립 완료 판정** — 이것 하나만 보고 됐다/안 됐다를 말할 수 있는가?

하나라도 아니면 앞뒤 항목과 합친다. 셋 다 통과하면 개수가 몇이든 그대로 둔다.

**서브태스크 0개도 정답이다**: 서버와 화면을 한 번에 고쳐야 눈에 보이는 변화가 나오는 스토리는 스토리 자체가 머지 단위다. 억지로 채우지 않는다.

**요구사항이 곧 작업은 아니다**: FR 목록을 순서대로 서브태스크에 옮기면 거의 항상 과분해된다. FR은 "무엇이 충족돼야 하는가"이고 서브태스크는 "한 번에 무엇을 고치는가"다. 여러 FR이 한 번의 수정으로 동시에 충족되는 일이 흔하다.

## 출력 템플릿

확정된 레벨로 `Proposed Issue Breakdown` 섹션을 채운다.

### L1 Single

```markdown
## Proposed Issue Breakdown

단일 작업으로 한 PR 범위. Epic/Story 트리 대신 작업 1건으로 등록한다.

- **작업**: <한 줄 요약>
  - 범위: <변경 파일/모듈 한 줄>
  - 검증: <측정 가능한 완료 기준 한 줄>
```

### L2 Story+Subtasks

```markdown
## Proposed Issue Breakdown

한 영역의 다단계 작업. Epic 없이 Story 1건과 Sub-task N개로 등록한다.

- **Story**: <스토리 한 줄 요약>
  - Sub-task 1: <서브태스크 요약>
    - 범위: <이 서브태스크가 독점하는 파일/모듈>
  - ... (파일군 덩어리 수만큼. 0개도 정답)
```

### L3 Epic+Stories+Subtasks

```markdown
## Proposed Issue Breakdown

여러 영역에 걸친 작업. Epic + Story + Sub-task 트리로 등록한다.

- **Epic**: <에픽 1줄 요약>
  - **Story 1**: <스토리 요약>
    - Sub-task 1.1: <서브태스크 요약>
      - 범위: <이 서브태스크가 독점하는 파일/모듈>
    - ... (파일군 덩어리 수만큼)
  - **Story 2**: <스토리 요약>
    - (서브태스크 없이 스토리 자체가 머지 단위여도 된다)
```

> 위 템플릿의 `Sub-task` 줄은 **모양 예시이지 채워야 할 슬롯이 아니다.** 스토리마다 서브태스크를 같은 개수로 맞출 이유가 없고, 서브태스크가 없는 스토리가 섞여도 된다. 채우기 전에 "서브태스크 도출 순서"의 파일군 나열을 먼저 끝낸다.

공통 규칙:
- 각 항목은 명사구 또는 동사구 한 줄 요약
- **모든 Sub-task는 `범위:` 자식 줄을 가진다** (필수). 파일/모듈을 특정할 수 없으면 그 항목은 서브태스크가 아니다 — 앞뒤와 합친다
- 두 서브태스크의 `범위:`가 겹치면 합친다
- 의존성 추정은 선택. 명시할 수 있으면 `(blocks: ...)` 등으로 표기
- L2/L3 트리 산출물은 `/jira-task create --from-requirements <경로>`로 일괄 등록 가능. L1은 `/jira-task create <자연어 힌트>`로 단건 등록 (import 파서가 Single 미지원)

## 사용자 변경

추천 레벨은 `Step 4.5 synthesis-confirm`에서 합성 결과와 함께 표시되며, 사용자가 `revise`로 다른 레벨을 지정 가능. 자유 입력 예: "L3 Tree로 바꿔줘" / "Single로 충분".

## Step 5에서 호출 흐름

1. `synthesis-confirm` proceed 통과 시 추천 레벨이 함께 확정된 상태로 진입.
2. "서브태스크 도출 순서"의 1-4를 수행해 파일군 → 서브태스크를 확정한 뒤, 본 파일의 출력 템플릿 중 확정 레벨 1개를 골라 문서 마지막 부분에 채움 (`범위:` 줄 포함).
3. `Technical Approach Hint` 섹션은 분해 레벨과 무관하게 항상 채운다 (요구사항 문서 말미 섹션).
